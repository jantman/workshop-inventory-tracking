## Intent

**Problem:** FR28/FR29/FR31 are entirely unrealized: `products` has no `stock_status` or `stock_status_at` — the `Product` docstring still reserves both for this story (`app/database.py:863-874`), and `grep -rn "stock_status" app/` matches only that reservation and the seam prose inside `Product.is_effective_low`. So the operator has no way to say "this is low" about a product they are not counting, which is the epic's whole point: FR30's Effective Low is defined as the OR of a *manual assertion* and the threshold comparison, and today only the second branch exists. Story 5.2 built `Product.is_effective_low` as a `@hybrid_property`/`@expression` pair and named, in both bodies' docstrings, exactly where this story's `or_` term goes (`app/database.py:982-1046`); until it lands, `docs/user-manual.md:850-861` states the low rule exhaustively to the operator in sentences that are about to become false.

**Approach:** Add two columns to `products` in a single Alembic revision — `stock_status` (`String(32)`, `NOT NULL DEFAULT 'unknown'`) and the nullable `stock_status_at` — backed by a new `StockStatus` enum in `app/models.py` whose values are the stored strings. Widen `Product.is_effective_low`'s two existing bodies with one `or_`/`or` term apiece and nothing else. Accept the status as a `<select>` on both product forms through the shared validator and a new `_apply_stock_status_assertion` in the catalog service — the sole writer of the pair, mirroring `_apply_quantity_assertion`'s settled stamp rule so an unrelated edit never re-dates the assertion. Surface the stored status plus the age of its assertion as one new route-computed detail row, and let the existing `Reorder signal` row start answering to manual flags.

## Boundaries & Constraints

**Always:**
- **The predicate stays single-sourced, and this story only widens it.** The stored-status branch is one `or` term in `Product.is_effective_low`'s Python getter and one `or_` term in its `@expression` — those two bodies and nowhere else (AD-6). The property is not renamed, not moved, not split into helpers: `TestTheComparisonHasExactlyOneHome` (`tests/unit/test_product_model.py:486-580`) asserts the threshold comparison has exactly two sites both named `Product.is_effective_low`, and a refactor into a `_low_by_threshold` helper breaks it. The threshold branch keeps its leading `IS NOT NULL` guards and its position; the status term is added *beside* it, not folded into it.
- **`stock_status` is `NOT NULL` with a `'unknown'` default, and that is load-bearing for the SQL half.** `cls.stock_status.in_(...)` on a nullable column is NULL for a NULL row, and `or_(NULL, FALSE)` is NULL — which is precisely the three-valued-logic trap the expression's existing docstring (`app/database.py:1033-1043`) says the `IS NOT NULL` guards exist to avoid, and it would silently drop rows from `filter(~Product.is_effective_low)`. Declare **both** `default='unknown'` (Python-side, so the value is in the INSERT and readable off the instance the moment `create_product` snapshots it after `flush()`) **and** `server_default='unknown'` (so the one `op.add_column` backfills every existing row, and so `Base.metadata` structurally matches the migrated schema — `tests/integration/test_migrations.py:194-211` diffs them).
- **The four values are single-sourced as a `StockStatus` enum in `app/models.py`**, stored as the string value in a plain `String(32)` column — no `sa.Enum`, no `CheckConstraint` — matching `IdentifierType`'s stated rationale (`app/models.py:119-137`): "so later stories can extend the set without a migration". Values are lowercase (`unknown`/`ok`/`low`/`out`) because `is_effective_low`'s existing docstring already committed to `stock_status IN ('low', 'out')`; the enum docstring must say why, since `ScanKind` is the repo's only other lowercase enum and it is explicitly never persisted. The *set that means low* is likewise one name in `app/models.py` (a module-level frozenset), imported by `app/database.py:21`'s existing `from .models import ...` line — a second literal `('low', 'out')` anywhere is a defect on the same footing as a second threshold comparison.
- **`_apply_stock_status_assertion(product, value)` in `app/mariadb_catalog_service.py` is the only writer of the pair**, called from both `create_product` and `update_product`, exactly as `_apply_quantity_assertion` (`:310-373`) is for the quantity pair and for the same stated reason (create and update cannot drift). `stock_status` joins `_PRODUCT_FIELDS`; `stock_status_at` does **not**, and gains an exclusion comment mirroring `quantity_verified_at`'s (`:46-52`) — a caller who could set it could claim an assertion was made at a time no one made it.
- **The stamp moves on a *changed* status, never on mere key presence.** This is Story 5.1's settled rule (`app/mariadb_catalog_service.py:337-342`) and it matters *more* here: a `<select>` with a non-empty default posts its key on every single edit, so a presence trigger would re-date the assertion every time the operator fixes a typo — defeating the staleness signal FR31 exists to surface. Concretely: `unknown` ⇒ status `unknown` and `stock_status_at = NULL` (no assertion has been made, mirroring how a blank quantity clears its stamp); any of `ok`/`low`/`out` ⇒ stamp moves to `datetime.now()` only when the submitted value differs from the stored one, **or** when the stored status is already non-`unknown` with a `NULL` stamp (the repair clause, mirroring `:367`). Comparisons read the stored value, so assign `stock_status` last.
- **`None` at the service means "not provided"; blank does not mean "clear".** `create_product(..., stock_status=None)` and an absent update key leave the column at its default/stored value untouched. Unlike the count fields there is no clear-to-NULL — the column cannot be NULL, and `unknown` is how "no assertion" is spelled — so `''`, whitespace, a non-string, or any value outside the enum is **refused** with `ValueError`/`TypeError` naming the field, its quoted value bounded by the existing `_truncated_for_refusal` (`:208-217`) because refusal text becomes `error_details` in the audit log. `update_product` returns `False` and `create_product` returns `None` on refusal, through the existing except-log handler; nothing is written.
- **Naive local `datetime.now()`**, plain `DateTime` column, no `server_default`, no `func.now()` — the repo-wide convention (`app/mariadb_catalog_service.py:357-361`) and what makes the stamp comparable by `app.utils.age_display.describe_age`.
- **Validation lives in the shared `_validate_product_form`** (`app/main/routes.py:917-1028`), keyed `stock_status`, because the control renders on both forms and `_validate_product_create_form`'s docstring holds that a route may not refuse a write over a field it neither renders nor reads (DW-13/DW-29). Fires only when the key is **present**: an absent key is the untouched case. A present value outside the four is an error, **and so is a present blank** — there is no blank state for this field. The message enumerates the four stored values and is built from the enum so it cannot drift. Add `stock_status` to `edit.html`'s `keyed_error_fields` (`:25`) and to `KEYED_FIELD_CASES` (`tests/unit/test_product_routes.py:5700-5725`) together — `test_the_parametrized_names_are_the_templates_own_list` parses the template's own list and compares.
- **Add/edit parity.** The same `<select>`, same `name`/`id`/option list/`is-invalid`+`invalid-feedback` pattern, on both `product/add.html` and `product/edit.html`. Options come from the route (both `_render_product_add` and every `product_edit` render site), never from the template importing the enum — the `identifier_type` select at `add.html:228` is the idiom. There is **no empty first option**: unlike `identifier_type`, this field has a real default, and `unknown` is it.
- **Layout: the two documented pairings survive.** Insert the status as a fifth `col-sm-6` cell immediately after `reorder_threshold`, followed by a `<div class="w-100"></div>` row break, so line 1 stays quantity+threshold, line 2 is the status alone, line 3 stays location+sub_location. Both templates' grid comments (`add.html:126-153`, `edit.html:166-178`) already reason about the 576–767 px band and must be updated to state that the break is what keeps that band's behaviour unchanged. Do not disturb `#stock-and-location`, the existing ids, or the two `*-suggestions` divs.
- **One `now` for the whole detail page.** `product_detail` renders two ages after this story; `describe_age`'s docstring asks for an explicit `now` in exactly that case, so compute `datetime.now()` once and pass it to both calls.
- **Display strings are finished by the route** (AD-5), from one mapping used by *both* the select's option labels and the detail row, so the operator never sees two names for one value: `unknown`→`Not set`, `ok`→`OK`, `low`→`Low`, `out`→`Out of stock`. The detail row appends `(set <age> ago)` only when the stamp exists, mirroring the quantity row's `(counted …)` — and gated on the *status*, not the stamp, for the same reason the quantity age is gated on the quantity (`app/main/routes.py`'s comment about `Not tracked (counted 3 months ago)`).
- Both new columns join `Product.to_dict()` (`app/database.py:1052-1082`), `stock_status_at` as `.isoformat()`-or-`None` like `quantity_verified_at` — that dict is the audit snapshot. `is_effective_low` stays out of it, as its comment requires.
- Catalog rows are read/written by `CatalogService`; routes hold no ORM/SQL (AD-1/AD-2). No `float`; no `>>>` prompts outside `app/utils/`.

**Block If:**
- The `or_` term cannot be added without restructuring `is_effective_low` such that `TestTheComparisonHasExactlyOneHome`'s "exactly two sites, both `Product.is_effective_low`" assertion no longer describes the code.
- The migration proves to need anything beyond two `op.add_column` calls on `products` (a data backfill beyond the server default, a constraint, an index, or a change to any other table).

**Never:**
- Do not add a "re-assert" checkbox analogous to `quantity_recounted`. The recount box exists because re-counting to the *same number* is a distinct workshop act; this story's age answers "when did you last change this", and the manual must say so. Adding the control is a design decision, not an implementation detail.
- Do not add an index. DW-250 asks to re-check indexability once `stock_status` widens the predicate; the answer recorded by this story is **no index yet** — this story adds no query consumer (Story 5.6 does), `stock_status` is a four-value low-cardinality column, and the OR'd threshold branch still forces a scan, so an index here would be speculative. Do not add a generated/virtual column (AD-6 forbids it).
- Do not add `stock_status` to `_PRODUCT_PREFILL_ARGS` (`app/main/routes.py:1299`). That whitelist is read from `request.args`, so membership would let a query string put a stock assertion in front of the operator, and a duplicated product has had no assertion made about it. Record the decision as a comment; leave DW-249's threshold question untouched.
- Do not compute or render On Order or Recently Received (Story 5.4). Do not make receiving a Purchase clear a manual low (Story 5.5) — nothing on the purchase path may write either new column. Do not build a reorder list, view, route or service query method (Story 5.6). Do not add group/sibling behaviour (Epic 10).
- Do not add a JSON endpoint, and therefore no `app/api_client.py` change. Do not put the status in `product/search.html` or `tag_products.html`, and do not touch `search_products` or its reserved `filters` argument (Epic 8's).
- Do not persist the derived signal: no column, no `to_dict()` key, no cache, no trigger. Do not add a standalone `set_stock_status` service method — the repo has no per-column mutator for `products` and `create_product`/`update_product` are the write path.
- Do not alter `_apply_quantity_assertion`, `_parse_stored_count`, or the two refusal messages Story 5.2 pinned byte-identical.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| New product | Created with no status argument | `stock_status = 'unknown'`, `stock_status_at IS NULL`, `is_effective_low` is `False` | No error expected |
| Manual low, nothing tracked | `quantity_on_hand IS NULL`, `reorder_threshold IS NULL`, status set to `low` | `is_effective_low` is `True` in Python **and** the row is returned by `filter(Product.is_effective_low)`; stamp set; no quantity column written (FR28/FR29/FR31) | No error expected |
| Manual out | status `out` | `True`, both encodings | No error expected |
| Manual ok, below threshold | `quantity_on_hand=2`, `reorder_threshold=3`, status `ok` | `True` — the threshold branch stands alone; setting `ok` does not suppress it (FR30, AD-6) | No error expected |
| Manual ok, no threshold | status `ok`, both count fields NULL | `False` | No error expected |
| Unknown status | status `unknown`, count 4, threshold 3 | `False`; the row appears in `filter(~Product.is_effective_low)`, not lost to a NULL | No error expected |
| Evaluation is read-only | Any product, property read then session inspected | `session.dirty` empty, `updated_at` unchanged, no `UPDATE` issued | No error expected |
| First assertion stamps | Status moves `unknown` → `low` | `stock_status_at` set to now | No error expected |
| Re-posting the same status | Rendered edit form re-posted with only `description` changed | `stock_status` unchanged **and `stock_status_at` unchanged** | No error expected |
| Changed status re-stamps | Status moves `low` → `out` | Stamp moves to now | No error expected |
| Clearing the assertion | Status moves `low` → `unknown` | `stock_status = 'unknown'`, `stock_status_at` cleared to `NULL`; detail row shows `Not set` with no age | No error expected |
| Missing stamp repaired | Stored status `low` with `stock_status_at IS NULL`, `low` re-posted | Stamp set to now | No error expected |
| Key absent | Edit body has no `stock_status` key | Both columns untouched | No error expected |
| Bad form value | `stock_status` present as `''`, `LOW`, `Low`, `bogus`, or 5000 characters | Form re-renders 200 with a keyed error naming the four values; nothing written | Keyed `validation_errors['stock_status']` |
| Bad caller value | `update_product(id, stock_status='bogus')` or `=7` or `=''` | Refused with `ValueError`/`TypeError` naming the field, value truncated; `update_product` returns `False`, `create_product` returns `None`; nothing written | Service-level raise, caught by the existing except-log handler |
| Audit snapshot | Any status write | `to_dict()` carries `stock_status` and `stock_status_at` (ISO or `None`) | No error expected |
| Status write leaves counts alone | Product with a tracked count, stamp backdated; status set to `low` | `quantity_on_hand`, `quantity_verified_at`, `reorder_threshold` all unchanged | No error expected |
| Detail rendering, manual low | Status `low`, stamp 3 days old | `Stock status` row reads `Low (set 3 days ago)`; `Reorder signal` row reads `Low stock` | No error expected |
| Detail rendering, unknown | Fresh product | `Stock status` row reads `Not set` with no parenthetical; `Reorder signal` reads `—` | No error expected |
| Receipt untouched | Recording/receiving a Purchase for a product with a manual `low` | Both new columns unchanged (Story 5.5's job, not this one) | No error expected |

## Design Notes

**Why `NOT NULL DEFAULT 'unknown'` rather than a nullable column.** The expression's existing docstring already establishes that a NULL inside this predicate is not a cosmetic concern: `filter(...)` looks correct while `filter(~...)` silently drops rows, because `NOT NULL` is `NULL`. `cls.stock_status.in_(('low','out'))` is `NULL` for a NULL row, and `or_(NULL, FALSE)` is `NULL` — so a nullable status column would reintroduce exactly the bug the `IS NOT NULL` guards were written to prevent, and would need its own `coalesce` guard to be safe. Making the column `NOT NULL` with a default removes the failure mode instead of guarding it, and it also gives `unknown` a single unambiguous spelling: there is no "NULL vs `unknown`" distinction for anyone to get wrong. The cost is that the `op.add_column` must carry a `server_default`, which is precedented (`vendor_scope`, `precision`).

**Why the stamp rule is "changed value", not "key present".** Story 5.1 shipped a presence trigger and had to revert it: the edit form re-posts every pre-filled value, so fixing a typo in the description re-dated the count. A `<select>` is *worse* than a text input here — it always posts, and it always posts a valid value, so there is no blank-means-untouched escape hatch. Hence the same changed-value test, with the same `NULL`-stamp repair clause, and the deliberate absence of a re-assert checkbox: unlike a recount, "still low" is not an act that produces new information the system has no other record of.

**Why `unknown` clears the stamp.** `unknown` is not a fourth opinion about the stock; it is the absence of an opinion, exactly as `quantity_on_hand IS NULL` is the absence of a count. `_apply_quantity_assertion` clears its stamp when the count is cleared, and leaving a date behind on a status of `Not set` would show the operator "set 3 months ago" next to a field asserting nothing.

**Why blank is a refusal at the service where it is a clear for the counts.** `_parse_stored_count` maps blank to `None` because its columns are nullable and `None` is a real state. `stock_status` cannot be `NULL`, so blank has no destination; mapping it silently to `unknown` would make a truncated or malformed POST quietly erase a `Low` flag. `None` (argument omitted) remains the no-op, which is what create and an absent update key rely on.

**What the existing tripwire does and does not cover.** `TestTheComparisonHasExactlyOneHome` walks `ast.Compare` nodes for subtrees naming *both* count columns. The new status term is a membership test, not an ordering comparison, and in the SQL half it is a `.in_()` *call* rather than a `Compare` — so the existing test neither breaks nor protects it. Extending it is what keeps the second half of the third acceptance criterion true, and the extension has to catch both spellings.
