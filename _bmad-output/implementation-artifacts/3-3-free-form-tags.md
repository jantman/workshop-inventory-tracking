## Intent

**Problem:** FR16 — "Products support zero or more free-form Tags, independent of Category" — has no implementation at any layer. The `product_tags` table the architecture's ERD specifies (`ARCHITECTURE-SPINE.md:224-228`, addendum `:70-71`) does not exist, `CatalogService` has no tag surface, the product add/edit form has no tag field, the detail page never shows one, and there is no way to retrieve a set of products by anything. Story 3.1 and 3.2 built the category half of Epic 3; the cross-cutting half that a hierarchy cannot express is entirely missing, and with it the epic's only stated retrieval behavior.

**Approach:** Add a `product_tags` child table (`product_id`, `tag`, unique on the pair) on the shared `Base`, fed by a new pure `app/utils/tag.py` that defines the canonical form of a tag and parses the operator's comma-separated input — the same pure-util-plus-service shape `app/utils/category.py` established for paths (AD-4). `CatalogService` gains a replace-all `set_product_tags`, plus `get_tags_for_product`, `list_tags` and `find_products_by_tag` — the last being FR16's filter. The product form gets one comma-separated `tags` input wired to the existing autocomplete-with-create component via a new opt-in multi-value mode (AD-14), the detail page renders tags as links, and two server-rendered pages (`/products/tags` listing every tag with its product count, `/products/tags/filter?tag=` listing the products carrying one) give the filter an operator-visible surface — the shape Story 3.2 set with `/products/categories`.

## Boundaries & Constraints

**Always:**
- `app/utils/tag.py` is **pure**: stdlib only, no Flask/SQLAlchemy/`app.*` imports (absolute or relative, and no `from .`), no I/O; its only failure signal is a module-local `InvalidTagError(ValueError)`. It carries a purity-guard test class modelled on `tests/unit/test_category.py:151` (AD-4, NFR7).
- The canonical form of a tag is defined **once**, in that util: trimmed, internal whitespace runs collapsed to one space, lowercased, at most `MAX_TAG_LENGTH` (64) characters, and never containing the `,` separator. Normalization never rewrites tag contents otherwise (no slugging, no Unicode folding beyond `str.lower()`) — the same rule `normalize_category_path` states at `app/utils/category.py:21-24`. Blank is **not** an error: `''`, `'   '`, `','`, `None` all mean "no tags" and yield an empty list.
- `parse_tag_list` de-duplicates on the canonical form preserving first-seen order, so "a tag is unique per Product" holds before the database is ever asked, and bounds the list at `MAX_TAGS_PER_PRODUCT` (50). Its rejection messages are operator-readable — the route renders them verbatim on the field.
- `CatalogService.set_product_tags(product_id, tags)` is **replace-all and idempotent**: it diffs the requested set against the stored rows on one `self.Session()`, reaches exactly one `commit()`, and returns the final sorted list. Every rejection is an `app.exceptions.ValidationError` raised past a `session.rollback()` in the `except ValidationError:` arm — the `add_identifier`/`add_attachment` pattern (`app/mariadb_catalog_service.py:1199-1210`). Do **not** adopt `create_product`/`update_product`'s swallow-and-return-`None` convention.
- A uniqueness collision surfaces as a `ValidationError`, never a raw `IntegrityError`: flush the inserts, and on `IntegrityError` roll back, re-query to confirm the duplicate, and re-raise the original if it was something else — `add_identifier:1175-1197`. This is reachable on MariaDB and not on SQLite: `utf8mb4_unicode_ci` folds accents (`café`/`cafe`) that the Python canonical form keeps distinct.
- Wherever the collation could decide an answer, **SQL narrows and Python decides** — the rule `list_category_paths` states at `app/mariadb_catalog_service.py:523-535`. `list_tags` groups and counts in Python; `find_products_by_tag` filters the joined rows on exact string equality after the query.
- The `tags` autocomplete reuses `app/static/js/field-autocomplete.js` **in place** via a new opt-in `multiValueSeparator` option (AD-14). With the option unset the class behaves byte-identically, so the five inventory fields and Story 3.1's `category_path` instance are untouched. The browser never derives the canonical form — the `+ Create` candidate is the server's `normalized` echo, as at `field-autocomplete.js:191-195`.
- `FIELD_SUGGESTION_COLUMNS` gains a `tags` entry and both of its registered rules — the echo branch in `normalize_suggestion_value` (`:344`) and the matching branch in `get_field_value_suggestions` (`:426`) — so the single `/api/inventory/field-suggestions/<field>` endpoint keeps dispatching on whitelist membership alone. Responses for the five inventory fields stay byte-identical.
- The schema change is one Alembic migration chained from head `f8e66632ee42`, authored by hand in the house style (`migrations/versions/3beb9dff5e41_add_product_identifiers_table.py`): explicit constraint names, `downgrade()` is `op.drop_table` only.
- New tests carry `@pytest.mark.unit` or `@pytest.mark.e2e` and use the house parametrize idiom (one case per line with an aligned trailing `#` comment), citing FR16/AD-4 in docstrings. E2E tests mint a unique tag prefix per invocation and assert only positively — `clear_test_data()` never truncates `products` and will not truncate `product_tags` (`tests/e2e/test_server.py:311-332`).

**Block If:**
- `nox -s tests` is already red on this branch before any change — pre-existing breakage, not this story's.
- Delivering the tag filter would require changing what Story 3.1/3.2 store in `products.category_path` or how they normalize it.

**Never:**
- No change to `products` — no column added, no data migration, no touch to `app/utils/category.py`, `normalize_category_path`, `list_category_paths` or `rename_category_path`.
- No global tag vocabulary table, no tag rename/merge/delete operation, and no tag hierarchy. The vocabulary is the distinct set of assigned `product_tags.tag` values, accreting purely from use (FR15's spirit); a tag disappears when the last product drops it.
- No combined category+tag faceting, no multi-tag AND/OR filtering, no bookmarkable multi-facet state, no free-text search — Epic 8 (8.1/8.2) owns all of it. This story's filter takes exactly one tag.
- No chip/token widget, no new JS file, no new dependency, no build step, no change to the five existing `field-autocomplete.js` instances or to `/api/inventory/field-suggestions/<field>`'s response shape for inventory fields.
- No change to inventory or metal-stock behavior (NFR9), and no `docs/user-manual.md` Products chapter — its absence is already an open deferred-work entry.

|----------|--------------|---------------------------|----------------|
| Canonical form | `normalize_tag('  SSR  Relay ')` | `'ssr relay'` — trimmed, collapsed, lowercased | No error |
| Blank is not an error | `normalize_tag('')`, `('   ')`, `(None)` | `None` — "no tag" | No error |
| Separator inside a tag | `normalize_tag('a,b')` | rejected — a tag cannot contain the list separator | `InvalidTagError` |
| Over-length tag | 65 canonical characters | rejected | `InvalidTagError` naming the limit |
| Non-string tag | `normalize_tag(5)` | rejected as a caller fault | `InvalidTagError` |
| Parse a list | `parse_tag_list(' SSR, rectifier ,, ssr ')` | `['ssr', 'rectifier']` — blanks dropped, de-duplicated on canonical form, first-seen order | No error |
| Parse nothing | `parse_tag_list('')`, `(',')`, `(None)` | `[]` | No error |
| Too many tags | 51 distinct tags | rejected before any write | `InvalidTagError` naming the 50 limit |
| Format for round-trip | `format_tag_list(['ssr', 'rectifier'])` | `'ssr, rectifier'` | No error |
| Assign tags | product with none; `set_product_tags(id, ['SSR', 'ssr', 'rectifier'])` | two rows written; returns `['rectifier', 'ssr']` (sorted) | No error |
| Replace-all | product tagged `a`,`b`; `set_product_tags(id, ['b', 'c'])` | `a` deleted, `b` kept (same row), `c` inserted; one commit | No error |
| Idempotent re-apply | same list applied twice | second call writes nothing and returns the same list | No error |
| Clear tags | `set_product_tags(id, [])` | every row for that product deleted; returns `[]` | No error |
| Unknown product | `set_product_tags(9999, ['x'])` | rejected; nothing written | `ValidationError(field='product_id')` |
| Collation-folded duplicate | MariaDB; `set_product_tags(id, ['café', 'cafe'])` | rejected; nothing written for that product | `ValidationError(field='tags')` naming the conflicting tag |
| Read back | product tagged `ssr`,`rectifier` | `get_tags_for_product` → `['rectifier', 'ssr']` alphabetical | No error |
| Tag vocabulary | 3 products: two tagged `ssr`, one `rectifier`, one untagged | `list_tags()` → `[('rectifier', 1), ('ssr', 2)]` alphabetical | No error |
| **FR16 filter** | 3 heat sinks at `thermal/heat-sinks`, two tagged `ssr`, one `rectifier`; plus an `ssr`-tagged product under another category | `find_products_by_tag('ssr')` → exactly the three `ssr` products, ordered by description, independent of category | No error |
| Filter normalizes its argument | `find_products_by_tag('  SSR ')` | same result as `'ssr'` | No error |
| Filter on nothing | `find_products_by_tag('')`, `(None)`, over-length, comma-bearing | `[]` — unmatchable, never "no filter" | No error |
| Suggestions | tags `ssr`, `ssr relay`, `rectifier`; `get_field_value_suggestions('tags', 'ss')` | `['ssr', 'ssr relay']` — exact, then starts-with, then contains; case-insensitive; distinct | No error |
| Suggestion echo | `normalize_suggestion_value('tags', ' SSR ')` | `'ssr'`; an over-length or comma-bearing query yields `None` (no create offered) | No error |
| Add with tags | POST `/products/add` with `tags='ssr, rectifier'` | product created, both tags stored, 302 to the detail page | No error |
| Add, invalid tags | POST with a 65-character tag | 200 re-rendering the form with the util's message on the `tags` field; **no product created** | Message rendered on the field |
| Edit round-trip | GET `/products/edit/<id>` for a product tagged `ssr`,`rectifier` | the `tags` input holds `rectifier, ssr` | No error |
| Edit clears tags | POST edit with `tags=''` | every tag row for that product removed | No error |
| Edit omits the key | POST edit with no `tags` key at all | tags untouched — absent means "not provided", the existing partial-update rule (`app/main/routes.py:988-991`) | No error |
| Tag write fails after the product saved | `set_product_tags` raises after a successful create/update | 302 to the detail page with an `error` flash saying the product saved but its tags did not — never a success flash, never a claim the product failed | Flash on the detail page |
| Tags on the detail page | product tagged `ssr`,`rectifier` | both rendered as badge links to `/products/tags/filter?tag=…`; an untagged product shows the `—` fallback | No error |
| Tag listing page | `GET /products/tags` | 200; every tag with its product count and a link; empty state when nothing is tagged | No error |
| Filter page | `GET /products/tags/filter?tag=ssr` | 200; exactly the `ssr` products, each linking to its detail page | No error |
| Filter page, unused tag | `?tag=nosuchtag` | 200 with an empty state naming the tag — an empty result is an answer, not an error | No error |
| Filter page, blank/unusable tag | `?tag=` absent, blank, over-length or comma-bearing | flash + 302 to `/products/tags` | No error |

## Design Notes

**Why tags get a canonical form at all.** "Free-form" describes the *vocabulary* — nothing is pre-populated and no schema constrains what a tag may say — not the *storage*. Two invariants force a canonical form anyway: "a tag is unique per Product" is meaningless if `SSR` and `ssr` are different rows, and "filtering by a tag returns exactly the tagged products" is false if the filter is case-sensitive against values typed on different days. Lowercasing in one pure util makes both true under SQLite's binary collation *and* MariaDB's `_ci` one, and it is the same trade Story 3.1 already made for category paths, so the operator meets one rule rather than two. Contents are never otherwise rewritten: `heat sink` stays two words.

**The separator is a storage constraint, not a style rule.** The form carries tags as one comma-separated string (the `aliases` precedent at `app/admin/routes.py:75`, and the only shape `request.form.to_dict()` round-trips), so a tag containing `,` could not survive the round-trip. `normalize_tag` therefore rejects it outright rather than silently splitting — a caller that splits first never sees the error, and a hand-crafted POST gets a message instead of two tags it did not ask for.

**Replace-all, diffed, idempotent.** `set_product_tags` takes the whole set because that is what the form submits — there is no per-tag add/remove UI. It diffs rather than delete-all-then-insert so unchanged rows keep their identity and `created_at`, and so re-submitting an unchanged form writes nothing. Idempotence also makes the route's retry story trivial: the only way to recover from a failed tag write is to save the form again, and doing so is always safe.

```python
current = {row.tag: row for row in session.query(ProductTag).filter_by(product_id=pid)}
for tag in set(current) - set(requested):
    session.delete(current[tag])
for tag in [t for t in requested if t not in current]:
    session.add(ProductTag(product_id=pid, tag=tag))
```

**Why the product and its tags are two transactions.** `create_product` is the sole writer of `internal_id` and owns a retry loop over its own session (`:171-232`); threading a second table through it would entangle tag failures with internal-id collision recovery. Instead the route validates tags *purely, before any write* — so every operator-caused rejection happens before the product is created — and then calls `set_product_tags`. What remains is an infrastructure failure between the two calls, and the route reports it honestly: the product saved, the tags did not, and the operator is sent to the detail page (where the product demonstrably exists) rather than back to a form claiming the save failed. Saving again fixes it, because the replace is idempotent.

**Collation is where SQLite and MariaDB actually disagree.** `utf8mb4_unicode_ci` is case-insensitive *and* accent-folding, so `café` and `cafe` — two distinct canonical tags in Python — collide on the `(product_id, tag)` unique index in production and not in the unit fixture. The insert is therefore allowed to fail: the `IntegrityError` arm re-queries, confirms a duplicate and raises a `ValidationError` naming it, exactly as `add_identifier:1175-1197` does, so the operator sees a sentence instead of a 500. The same folding is why `list_tags` counts in Python and `find_products_by_tag` re-checks exact equality after the query — SQL narrows, Python decides, the division `list_category_paths` documents at `:523-535`.

**Multi-value autocomplete without a widget.** The architecture puts the tag input on the same autocomplete-with-create component as the category input (`ARCHITECTURE-SPINE.md:265`), but that component assumes one value per input: `buildUrl()` sends the whole field as `q` and `selectValue()` overwrites it. A `multiValueSeparator` option — unset by default, so the six existing instances are untouched — makes both operate on the fragment after the last separator instead. That is roughly fifteen lines against a chip/token widget's several hundred, it inherits the debounce, stale-response sequencing, keyboard navigation and dismissal logic unchanged, and the create affordance keeps working for free because the server still echoes the canonical form of exactly the fragment it was sent.

**Where the pages live.** On the `main` blueprint beside the other product routes, reaching `CatalogService` through `_get_catalog_service()` — the placement Story 3.2 argued for and set. `/products/tags/filter` takes the tag as a query parameter rather than a path segment because a canonical tag may contain spaces and `/`.
