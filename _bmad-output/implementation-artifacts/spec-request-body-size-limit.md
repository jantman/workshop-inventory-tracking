## Intent

**Problem:** The app imposes no transport-level bound on a request body, so an arbitrarily large JSON or multipart body is buffered and parsed in full before any application-level check can reject it (DW-47, DW-53). Every JSON route is `@csrf.exempt` and the app is unauthenticated, so the only existing ceilings are per-field guards that run after the body is already in memory: `POST /api/scan` bounds `raw` at 4096 chars only after `request.get_json(silent=True)`, and `ATTACHMENT_MAX_SIZE` / `PhotoService.MAX_FILE_SIZE` are checked after Werkzeug has buffered the upload.

**Approach:** Enforce the bound at the **WSGI layer**, by *controlling* the input stream rather than by *predicting* from headers whether a body is inbound. A middleware wraps `environ['wsgi.input']` in a counting stream that **raises** `RequestEntityTooLarge` as soon as a read would take the request past its cap, choosing the cap by matching the environ against the URL map so the two upload endpoints get the raised ceiling. A `before_request` hook keeps two narrow jobs: reject a declared, parseable, over-limit `Content-Length` early (the fast path every real client takes), and force the body read so a cap violation surfaces outside any view's `except Exception`. A `RequestEntityTooLarge` handler renders a coherent 413 in both the JSON and HTML branches.

**Why this shape, and not the `before_request` header classifier of iterations 1-4.** Four consecutive iterations were reverted, every one for the same root cause: a hook that inspects `Content-Length`, `Transfer-Encoding` and `wsgi.input_terminated` to *guess* whether Werkzeug will read a body, then either rejects (411) or trusts `request.max_content_length`. Iteration 3's guess took the whole app down under gunicorn; iteration 4's opposite guess let a body through truncated at exactly the limit with a 200. A capped stream has nothing to guess: a bodyless `GET` reads zero bytes and is untouched by construction, and any body — chunked, undeclared, or misdeclared — raises on the read that crosses the cap. **This removes the 411 rule, the three-state length classifier, `_plain_int` parity as a security control, and both of iteration 4's one-header remote 500s.**

## Boundaries & Constraints

**Always:**
- **`app.config['MAX_CONTENT_LENGTH']` must remain `None`.** This is the single load-bearing invariant of the design and it is counterintuitive enough that it needs its own test. `werkzeug.wsgi.get_input_stream` (verified in the installed 3.1.8) reaches `LimitedStream(stream, max_content_length, is_max=True)` — which **truncates rather than raising** — only when `max_content_length is not None` *and* `wsgi.input_terminated` is in the environ. With the key left `None`, the same branch returns the raw (i.e. middleware-capped) stream and the cap is authoritative. **Measured:** with the key set, an oversize body with no `Content-Length` under a gunicorn-shaped environ returns `200` carrying exactly `limit` bytes — the precise iteration-4 defect; with it left `None`, the identical request returns `413`.
- Because Flask owns the `MAX_CONTENT_LENGTH` config name, this project's own limits are named **`MAX_REQUEST_BODY_BYTES`** and **`MAX_UPLOAD_BODY_BYTES`**. Both live in `config.py` `class Config` as env-overridable class attributes, matching the existing `os.environ.get('X') or default` / `int(...)` idiom in that file. `TestConfig` inherits them unchanged so tests exercise the real bound.
- The upload ceiling must exceed the largest legitimate upload (`PhotoService.MAX_FILE_SIZE` = 20 MiB, `ATTACHMENT_MAX_SIZE` = 16 MiB − 1) plus multipart framing overhead, so the existing service-layer size checks remain the ones that produce the friendly error for merely-oversize files.
- Upload endpoints are identified by endpoint name (`main.product_upload_attachment`, `main.upload_photo`), not by URL string matching. The middleware resolves them by binding the environ to `app.url_map` inside a `try`, falling back to the global limit on **any** failure — a routing miss must never be able to raise out of the middleware, and falling back to the *tighter* limit is the safe direction.
- The middleware must normalise a non-`str` `CONTENT_LENGTH` in the environ to `str`. **Measured:** without it, `werkzeug.sansio.utils.get_content_length` calls `_plain_int`, which calls `.strip()`, raising `AttributeError` from inside *Werkzeug itself* — so this one cannot be fixed by making the app's own code total, only by repairing the environ before Werkzeug reads it.
- The `before_request` hook is still registered **before** `csrf.init_app(app)`. This is no longer what prevents the failure (a capped stream raises wherever the read happens, including inside `CSRFProtect`'s own hook), but the ordering keeps the rejection attributable to this feature rather than surfacing as a CSRF error.

**Block If:**
- The capped stream proves not to be reached — i.e. some path reads the body without going through `environ['wsgi.input']`, so a read past the cap neither raises nor is bounded.

**Never:**
- **Do not set `app.config['MAX_CONTENT_LENGTH']`, and do not set `request.max_content_length`.** Either one re-arms Werkzeug's truncating `LimitedStream` and silently restores the iteration-4 hole. If a future reader "notices" that Flask has a built-in limit and wires it up, this whole change regresses to a 200 carrying a truncated body.
- Do not add a `LengthRequired` / 411 branch. Undeclared and chunked lengths are handled by the cap; a 411 rule is what caused the iteration-3 production outage and it now buys nothing.
- Do not lower or remove `ATTACHMENT_MAX_SIZE`, `PhotoService.MAX_FILE_SIZE`, or `MAX_SCAN_LENGTH` — the transport bound is additive to them, not a replacement.
- Do not set a single global limit at 20+ MiB "to keep uploads working" — that leaves every unauthenticated JSON route accepting multi-megabyte bodies, which is the exposure being closed.
- Do not change `MAX_FORM_MEMORY_SIZE` (Flask's 500 KB default already bounds urlencoded bodies and per-field multipart parts, and it is unaffected by the `MAX_CONTENT_LENGTH` invariant above).
- Do not add rate limiting, authentication, or WSGI-server config; no changes to the deferred-work ledger.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Normal JSON scan | `POST /api/scan` with a small `{"raw": "..."}` body | Unchanged behavior (200 / existing 400s) | No error expected |
| Oversize JSON body, declared length | `POST /api/scan`, `Content-Length` over `MAX_REQUEST_BODY_BYTES` | 413 with a JSON body, rejected in `before_request`; no view code runs | `RequestEntityTooLarge` handler, JSON branch |
| Oversize JSON body, **no** declared length | Same body, `Content-Length` absent / `''` / `'   '`, `wsgi.input_terminated` set | 413 — the cap raises on the read that crosses it. **Never a 200 carrying a truncated body.** | `RequestEntityTooLarge` from the capped stream |
| Oversize body, chunked | `Transfer-Encoding: chunked`, no length | 413 (**not** 411) | `RequestEntityTooLarge` from the capped stream |
| Oversize HTML form POST | `POST /products/edit/<id>` (urlencoded/multipart) over the limit | 413 rendered as an error page | `RequestEntityTooLarge` handler, HTML branch |
| Attachment upload above global, below upload ceiling | `POST /products/<id>/attachments` multipart, ~2 MiB | Not rejected as 413; reaches the view and the existing `ATTACHMENT_MAX_SIZE` path | No 413 |
| Photo upload above global, below upload ceiling | `POST /api/items/<ja_id>/photos` multipart, ~2 MiB | Not rejected as 413; reaches the view | No 413 |
| Upload above the upload ceiling | Either upload endpoint, body over `MAX_UPLOAD_BODY_BYTES` | 413; not swallowed into a 500 by `upload_photo`'s broad `except Exception` | Raised in `before_request`, past the view's catch-all |
| Hostile `Content-Length` | `+50`, `1_0`, 5000 digits, or a non-`str` environ value | Rejected if the body is oversize; **never a 5xx** | Parse failure falls through to the cap |
| GET / HEAD / OPTIONS | Any such route, with or without `wsgi.input_terminated` | Unaffected — zero bytes read, so the cap is never approached | No error expected |

- `werkzeug/sansio/utils.py` `get_content_length` -- discards `Content-Length` only when `'chunked' in parse_set_header(Transfer-Encoding)`, not for any `Transfer-Encoding`. Under this design the hook's parse is not security-relevant, so a bare `except (ValueError, TypeError)` around it is sufficient and the request falls through to the cap — verified to yield `413`, not `500`.

Every claim in this spec about gunicorn's environ is therefore reasoned from its documented behaviour and cannot be executed in CI — which is an argument for predicates whose failure mode is bounded, not for confidence.

- [x] `app/request_limits.py` -- new module holding:
  - `UPLOAD_ENDPOINTS`, a frozenset of the two blueprint-qualified endpoint names.
  - `CappedStream`, a `wsgi.input` wrapper that counts bytes across **every** read path it exposes (`read`, `readline`, `readlines`, `__iter__`) and raises `RequestEntityTooLarge` the moment the running total exceeds its cap. It must never truncate and never return short. Anything Werkzeug's form parser or `get_data()` can call must be counted — an uncounted method is a silent bypass.
    - **It must also CLAMP every read, not merely count it afterwards.** `read(-1)`/`read(None)` — which is exactly what `Request.get_data()` issues for a JSON or urlencoded body — must never be passed through to the wrapped stream. **Counting after an unsized read bounds the response but not the memory**, which is the entire point of the feature: measured, a 64 MiB body against a 1 MiB cap returned a correct 413 *after* 64 MiB was resident. The multipart path happens to be safe (Werkzeug's `_chunk_iter` issues 64 KiB sized reads), so this defect hides on uploads and bites on every JSON route.
    - **The clamp must bound each INDIVIDUAL read to a small constant (use 64 KiB), not merely bound the total to `cap - already_read + 1`.** Reading the whole remaining allowance in one call is a second, worse defect, and it was measured on the iteration that first added the clamp: `io.BufferedReader.read(n)` — which is what the Werkzeug dev server hands you as `wsgi.input`, and what any socket-backed stream behaves like — **allocates `n` bytes up front before it knows how much data exists**. Measured: `BufferedReader.read(24 MiB)` over a **9-byte** body peaks at 24.00 MiB; end-to-end, a **7-byte** multipart POST to `/api/items/<ja_id>/photos` peaks at **24.03 MiB**. Because the `before_request` hook issues `get_data()` on *every* request, that is a cap-sized transient allocation on every request including bodyless ones — trading an allocation proportional to the attacker's body for one proportional to the configured cap, unconditionally. Loop `read`/`readline` in 64 KiB steps, accumulating until the caller's request is satisfied, the stream is exhausted, or the cap is broken.
    - `readline`, `readlines` and `__iter__` must be **genuinely** clamped, not merely handed a size hint. Passing `_allowed(size)` down to `self._stream.readline(...)` and counting the result trusts the wrapped stream to honour the hint; a stream that under-honours it materialises the whole body before `_count` ever runs (measured: 10,000,000 bytes pulled through a 1,000-byte cap). Loop them the same way `read` loops. A body with no newline in it is one enormous "line", so the size bound — not the newline — must be what terminates the read.
    - Do not accumulate chunks into a list and `b''.join` them without accounting for the copy: that peaks at **2×** the allowance, which contradicts any docstring claiming the allowance is the bound. Either state the real factor or assemble into a single pre-sized `bytearray`.
  - `BodyLimitMiddleware`, wrapping `app.wsgi_app`. It resolves the cap by binding the environ to `app.url_map` inside a `try` (falling back to `MAX_REQUEST_BODY_BYTES` on **any** exception), installs the `CappedStream`, and returns. It must not raise for any environ — including one with **no `wsgi.input` key at all** (PEP 3333 mandates it, but the docstring's totality claim is what justifies the design, so honour it: pass such an environ through untouched rather than `KeyError`ing).
    - It must normalise **every** environ value Werkzeug will parse as a string, not just `CONTENT_LENGTH`: at minimum `CONTENT_LENGTH` and `CONTENT_TYPE`. Measured on this iteration: a non-`str` `CONTENT_TYPE` raises `AttributeError: 'int' object has no attribute 'partition'` from inside `werkzeug.http.parse_options_header`, as a 500. The forced `get_data(parse_form_data=True)` below is what widens this from "views that touch the form" to **every route in the app**, so the hook and the normalisation are a matched pair.
  - The cap for the upload endpoints must additionally require the request to actually **be** an upload: apply `MAX_UPLOAD_BODY_BYTES` only when the mimetype is `multipart/form-data`, and `MAX_REQUEST_BODY_BYTES` otherwise. Endpoint identity alone is not enough — measured, an 8 MiB `application/json` body to the unauthenticated, `@csrf.exempt` `main.upload_photo` is accepted and cached under the 24 MiB ceiling, which hands back most of the exposure this feature exists to close. Require a non-empty `boundary` parameter as well, so the raised ceiling is not granted on a bare attacker-chosen header; and **record in the config comment that the content type is still caller-supplied**, so the honest statement of the bound is "24 MiB to the two upload endpoints for anything shaped like a multipart body", not "24 MiB only for real uploads".
  - `_cap_for` must read the limits with `.get(...)` and a literal fallback, never `config['...']`: a missing key is otherwise a `KeyError` out of the middleware, which is a bare 500 with no error handler — the one thing its docstring promises cannot happen.
  - The forced body read must not convert unrelated outcomes into a 413 or a raw Werkzeug error page. Specifically: a client that disconnects or under-sends its declared body raises `ClientDisconnected` from the hook on routes that never touch the body (measured: a raw Werkzeug 400); and an over-limit body sent to a URL that 404s, 405s or redirects is answered 413 instead of the real routing answer (measured). Let the routing answer win, and handle a disconnect as a disconnect.
  - `validate_limits(config, logger)`, raising `ConfigurationError` when a limit is missing, `None`, non-integer, `< 1`, above a sanity ceiling (a limit is now an allocation bound, so a single mistyped digit — `251658240` for `25165824` — otherwise boots clean while effectively removing the bound; reject anything implausible, e.g. over 1 GiB), or when `MAX_UPLOAD_BODY_BYTES` is **less than** `MAX_REQUEST_BODY_BYTES` — note **`<`, not `<=`**: equality is perfectly coherent (the upload endpoints simply get the same cap) and is the strictest uniform posture an operator can ask for, so refusing to boot on it makes the simplest configuration inexpressible, and logging a startup **warning** (not an error) naming every breached service floor. **Acceptance Criteria:**
- Given the app built from `Config` or `TestConfig`, when it is created, then `app.config['MAX_REQUEST_BODY_BYTES']` and `app.config['MAX_UPLOAD_BODY_BYTES']` hold the documented defaults and both are overridable by the same-named environment variables; a non-numeric override raises `ConfigurationError` naming the variable.
- **Given any app built by `create_app`, when it returns, then `app.config['MAX_CONTENT_LENGTH'] is None`.** And given it is set to the limit instead, when an oversize body with no `Content-Length` arrives on a terminated stream, then the response is a 200 carrying exactly `limit` bytes — the iteration-4 defect. Both directions must be tested, so the invariant is demonstrated rather than merely asserted.
- Given `MAX_UPLOAD_BODY_BYTES` at or below `MAX_REQUEST_BODY_BYTES`, when `create_app` runs, then it raises `ConfigurationError`; given it merely below `PhotoService.MAX_FILE_SIZE` or `ATTACHMENT_MAX_SIZE`, then the app starts and logs a warning naming the floors, so a deployer may deliberately choose a stricter upload posture.
- Given an oversize body posted to **any** JSON route whose view wraps its body read in a broad `except Exception` — `/api/inventory/batch-move`, `/api/inventory/search`, `/api/validate/type-shape`, `/api/labels/print`, `/api/photos/copy`, `/api/items/<ja_id>/duplicate`, `/admin/api/materials/validate` — when it is rejected, then the response is 413 with a JSON envelope and no view code ran, so no catch-all can downgrade it to a 500 or leak raw Werkzeug text. This must hold for a declared `Content-Length` **and** for no declared length at all.
- **Given `wsgi.input_terminated` set and no usable `Content-Length` (absent, `''`, or whitespace), when a body-carrying `POST` is made, then the response is 413 and the body never reaches a view truncated with a 200** — the failure measured against iteration 4 at exactly `MAX_CONTENT_LENGTH` bytes of a longer body.
- **Given `wsgi.input_terminated` set in the environ — which gunicorn sets on every request — when a `GET`, `HEAD`, `OPTIONS`, or bodyless `POST` is made to any route, then the response is byte-for-byte what it is without the flag.** In particular `GET /index` must not redirect to itself and nothing may return 411. This criterion is the whole reason iteration 3 was reverted.
- Given an oversize body with `Transfer-Encoding: chunked` and no `Content-Length`, when it is rejected, then the response is **413** — never 411, and never a truncated body reaching the view.
- Given `Transfer-Encoding: gzip` alongside a valid `Content-Length`, when the request is within the limit, then it is served normally.
- Given a hostile `Content-Length` — one plain `int()` accepts but `_plain_int` rejects (`+50`, `1_0`, non-ASCII digits), one of more than 4300 ASCII digits, or a non-`str` value in the environ — when an oversize body follows, then the response is 413 and **never a 5xx**. No header value or environ shape may produce a 5xx from the middleware, the hook, or the handler.
- Given a multipart POST under the limit but carrying a non-file field over Flask's 500 KB `MAX_FORM_MEMORY_SIZE`, when it is rejected, then the response is 413 with the JSON envelope rather than a 500 leaking `413 Request Entity Too Large: ...` from inside `upload_photo`'s catch-all.
- Given a rejected request to a route whose client reads `error` as a string (`/api/inventory/batch-move` → `inventory-move.js:704`), when the JSON body is rendered by that client, then it yields a human-readable sentence and never `[object Object]`; and given `/api/scan`, then `scan-capture.js`'s `data.error.message` resolves to that sentence.
- Given an oversize non-`/api` form POST, when it is rejected, then the response is **413 rendering `errors/413.html`, with no `Location` header** — regardless of what `Referer` carries, including `http://[::1`, `javascript://localhost/x`, and an external host. No request header may influence the response target.
- Given the app mounted under a non-root `SCRIPT_NAME`, when an oversize form POST to the mount's own path is rejected, then the response is a 413 — there is no redirect, so no self-redirect loop is possible at any mount point.
- Given an app built with `WTF_CSRF_ENABLED = True`, when a valid >1 MiB multipart attachment is posted to the attachment endpoint, then it succeeds; and when one over the upload ceiling is posted, then it is rejected with 413 rather than a CSRF error. This is a real request-level test, not a `before_request_funcs` name comparison.
- Given an unmodified deployment on the shipped defaults, when `create_app` runs, then it logs **no** WARNING — the mis-set-ceiling warning must stay meaningful, which it cannot if a second warning fires on every boot.
- Given `create_app` on the shipped defaults, when it returns, then PIL, PyMuPDF and the ORM have not been imported as a side effect of validating the limits.
- Given the full unit suite, when `nox -s tests` runs, then it passes with no new failures — in particular the existing attachment, photo, scan, and product-form tests.

### 2026-07-26 — Human escalation resolution (`/bmad-loop-resolve`)

**What escalated.** Not a spec ambiguity: the review session's recorded blocking condition was **"code revert denied by permission policy"** — it could not run `git checkout --` / `rm` to revert the iteration-4 tree before re-deriving. That mechanical blocker was cleared out of band; the working tree is at baseline `ad7299a` with both new files removed, and the iteration-4 diff is preserved as evidence.

**Why the resolution went further than unblocking.** Four consecutive dev→review cycles have now been reverted, and all four share one root cause: a `before_request` hook that *predicts from headers* whether Werkzeug will read a body. Pass 2 missed chunked; pass 3 keyed on `wsgi.input_terminated` and took the app down under gunicorn; pass 4 keyed on its negation and let bodies through truncated with a 200. Pass 5 as drafted was a fourth guess at the same predicate, against a premise (`gunicorn`'s environ) that no CI in this repo can execute. Re-arming the story unchanged would most likely have produced a fifth revert.

**Decisions taken with the human.**
1. **Stop predicting; control the stream.** Enforcement moves to a WSGI middleware that wraps `environ['wsgi.input']` in a counting `CappedStream` which raises rather than truncates. The `before_request` hook keeps only the declared-length fast path and a forced body read so the raise lands ahead of every view. This deletes the 411 rule, the three-state length classifier, `_plain_int` parity as a security control, and both of iteration 4's one-header remote 500s.
2. **The HTML 413 branch renders `errors/413.html` instead of redirecting.** This deletes the entire referrer subsystem — `_same_host_referrer`, `_redirects_to_self`, scheme validation, case/port-insensitive host comparison, `script_root` awareness — which produced four of pass 4's nine findings. Cost: an attachment uploader gets an error page rather than being returned to the product page.

**Verified, not reasoned — the amendment's premises were executed** against the installed Flask 3.1.3 / Werkzeug 3.1.8 on a probe app before being written down:
- `get_input_stream` reaches the truncating `LimitedStream(..., is_max=True)` **only** when `max_content_length is not None`; with it `None` and `wsgi.input_terminated` set it returns the raw stream unwrapped.
- With `MAX_CONTENT_LENGTH=None` + the middleware, a gunicorn-shaped oversize request returns **413** for `Content-Length` absent / `''` / `'   '` / chunked / 5000-digit / non-`str`, and `GET`/`OPTIONS` are unchanged at 200.
- With `MAX_CONTENT_LENGTH` **set**, the same no-length request returns **200 carrying exactly `limit` bytes** — the iteration-4 defect, reproduced on demand. Hence the new invariant and its two-directional test.
- Without the forced read in `before_request`, the same request returns **500**, swallowed by a view catch-all.
- A non-`str` `CONTENT_LENGTH` raises `AttributeError` from inside *Werkzeug's own* `_plain_int`, so it is fixable only by normalising the environ in the middleware — a case no amount of app-side totality would have caught.

## Design Notes

**Enforcement point: the WSGI stream, surfaced in `before_request`, never in the view.** Flask enforces a body limit lazily — the 413 is raised wherever the body is first touched. Most JSON views here read the body *inside* a `try` whose tail is `except Exception: return 500`, so a lazily-raised 413 is caught by the view and downgraded. Verified against an earlier implementation attempt: a 2 MiB body to `/api/inventory/batch-move` was swallowed, and the handler then died with `UnboundLocalError` on `ja_id` (bound only inside the loop the body read precedes). Adding `except RequestEntityTooLarge: raise` per view does not scale and silently omits every future view. So the bound is imposed on the stream itself, and the read is forced in `before_request` so the raise always lands ahead of every view — including views not yet written:

```python
UPLOAD_ENDPOINTS = frozenset({'main.product_upload_attachment', 'main.upload_photo'})
_FORM_MIMETYPES = ('multipart/form-data', 'application/x-www-form-urlencoded')


class CappedStream:
    """Wraps wsgi.input. Raises rather than truncating past `cap` bytes.

    Every read path must be counted AND CLAMPED -- an uncounted method is a
    silent bypass, and an unclamped one bounds the response without bounding
    the memory, which is the whole point.
    """

    def __init__(self, stream, cap):
        self._stream, self._cap, self._read = stream, cap, 0

    # Each individual read is bounded by this, NOT by the remaining allowance.
    # io.BufferedReader.read(n) -- what the dev server and any socket-backed
    # stream give you -- allocates n bytes UP FRONT, before it knows how much
    # data exists. Asking for the whole allowance therefore costs the whole cap
    # on every request, even a 7-byte one. Measured: 24.03 MiB peak for a
    # 7-byte multipart POST against the 24 MiB upload cap.
    _CHUNK = 64 * 1024

    def _room(self):
        # One byte past the cap is all it takes to know the cap is broken.
        return self._cap - self._read + 1

    def _read_bounded(self, size, reader, stop_on_newline=False):
        """Pull at most `size` bytes (unsized => the whole allowance) via
        `reader`, in `_CHUNK` steps, counting as we go.

        Loops because a WSGI stream may legitimately return short, and this
        class promises never to return short of what was asked for: a body
        UNDER the cap must arrive whole.
        """
        wanted = self._room() if size is None or size < 0 else min(size, self._room())
        out = bytearray()
        while wanted > 0:
            chunk = reader(min(wanted, self._CHUNK))
            if not chunk:                      # EOF
                break
            self._read += len(chunk)
            if self._read > self._cap:
                raise RequestEntityTooLarge()
            out += chunk
            wanted -= len(chunk)
            if stop_on_newline and chunk.endswith(b'\n'):
                break
        return bytes(out)

    def read(self, size=-1):
        return self._read_bounded(size, self._stream.read)

    def readline(self, size=-1):
        # A body with no newline in it is one enormous "line", so the SIZE
        # bound -- not the newline -- has to be what terminates this.
        return self._read_bounded(size, self._stream.readline, stop_on_newline=True)

    def readlines(self, hint=-1):
        # Built on the clamped readline above, NOT on the wrapped stream's own
        # readlines, which would read everything first.
        lines = []
        while True:
            line = self.readline()
            if not line:
                return lines
            lines.append(line)

    def __iter__(self):
        while True:
            line = self.readline()
            if not line:
                return
            yield line


class BodyLimitMiddleware:
    def __init__(self, wsgi_app, app):
        self.wsgi_app, self.app = wsgi_app, app

    def __call__(self, environ, start_response):
        # Werkzeug's _plain_int calls .strip() unguarded, so a non-str value
        # raises AttributeError from inside Werkzeug -- fix it here or nowhere.
        cl = environ.get('CONTENT_LENGTH')
        if cl is not None and not isinstance(cl, str):
            environ['CONTENT_LENGTH'] = str(cl)

        environ['wsgi.input'] = CappedStream(environ['wsgi.input'],
                                             self._cap_for(environ))
        return self.wsgi_app(environ, start_response)

    def _cap_for(self, environ):
        # Any routing failure falls back to the TIGHTER limit; this must not raise.
        try:
            endpoint, _ = self.app.url_map.bind_to_environ(environ).match()
            if endpoint in UPLOAD_ENDPOINTS:
                return self.app.config['MAX_UPLOAD_BODY_BYTES']
        except Exception:
            pass
        return self.app.config['MAX_REQUEST_BODY_BYTES']


def init_request_limits(app):
    validate_limits(app.config, app.logger)
    app.wsgi_app = BodyLimitMiddleware(app.wsgi_app, app)

    @app.before_request
    def enforce_request_body_limit():
        cap = (app.config['MAX_UPLOAD_BODY_BYTES']
               if request.endpoint in UPLOAD_ENDPOINTS
               else app.config['MAX_REQUEST_BODY_BYTES'])

        # Fast path only. A length we cannot parse is not a bypass -- it just
        # skips this branch and the capped stream still applies.
        raw = request.environ.get('CONTENT_LENGTH')
        try:
            declared = int(str(raw).strip()) if raw not in (None, '') else None
        except (ValueError, TypeError):
            declared = None
        if declared is not None and declared > cap:
            raise RequestEntityTooLarge()

        # Force the read HERE so a cap violation raises outside any view's
        # except-Exception. parse_form_data=True additionally moves the lazy
        # MAX_FORM_MEMORY_SIZE / MAX_FORM_PARTS 413s out of the view, and
        # avoids caching the raw bytes alongside the parsed upload.
        request.get_data(cache=True, parse_form_data=True)
```

**Why a capped stream instead of a header predicate.** Iterations 1-4 all tried to *decide from headers* whether Werkzeug would read a body, then rejected or trusted `request.max_content_length`. That question turns out to be genuinely hard — it depends on `wsgi.input_terminated`, which gunicorn sets on every request including every `GET`, on Werkzeug's `_plain_int` accepting a narrower grammar than `int()`, and on `LimitedStream(is_max=True)` truncating where every reader assumes it raises. Iteration 3 guessed one way and took the app down; iteration 4 guessed the other way and let bodies through truncated. A capped stream does not ask the question: a bodyless `GET` reads zero bytes and never approaches the cap, and any body raises on the read that crosses it, whatever the headers claimed.

**The load-bearing invariant: `app.config['MAX_CONTENT_LENGTH']` must stay `None`.** Read from the installed Werkzeug 3.1.8, `get_input_stream` wraps the stream in the truncating `LimitedStream(..., is_max=True)` **only** when `max_content_length is not None` and `wsgi.input_terminated` is present. Leave it `None` and that same branch returns the raw stream — i.e. the `CappedStream` — untouched, so the cap is authoritative. Measured on a probe app, gunicorn-shaped environ, oversize body, no `Content-Length`: `MAX_CONTENT_LENGTH=None` → **413**; `MAX_CONTENT_LENGTH=limit` → **200 carrying exactly `limit` bytes**. This is why this project's limits are named `MAX_REQUEST_BODY_BYTES` / `MAX_UPLOAD_BODY_BYTES` — putting them under Flask's own key would silently re-arm the truncation. It is also why the invariant needs a test that *demonstrates* the regression, not one that merely asserts `is None`: the assertion alone reads like a tidy-up and invites deletion.

**The forced read is load-bearing too.** Measured: with the middleware installed but no `request.get_data()` in `before_request`, an oversize body with no declared length raises inside the view, where the app's `except Exception` catch-alls turn it into a **500** — the exact swallowing this whole enforcement-point design exists to prevent. Reading in the hook moves the raise ahead of every view.

**`parse_form_data=True` is required, but not for the reason it looks like.** It is *not* needed to keep `request.files` working — `cache=True` alone does that, because the form parser falls back to the cached bytes (`Request.get_data`'s own docstring says so, and it is measured: files and form fields survive with `parse_form_data=False`). The two real reasons:

- **`MAX_FORM_MEMORY_SIZE` is untouched and still lazy.** Flask's 500 KB form-field limit (and `MAX_FORM_PARTS`) raise `RequestEntityTooLarge` from inside the parser. Measured with a tiny `MAX_FORM_MEMORY_SIZE` and an oversize non-file field: `parse_form_data=False` → **500, swallowed by the view's `except Exception`**; `parse_form_data=True` → **413 handled outside the view**. This is the load-bearing reason.
- **It avoids double-buffering every upload.** With `parse_form_data=True` the parser consumes the stream first and `get_data` then caches `b''`. Measured on a 200 KB multipart upload: `False` caches 200,237 raw bytes *on top of* the parsed file; `True` caches 0. On a 24 MiB photo that is ~24 MiB of avoidable duplication on an endpoint this spec already flags as reading files fully into memory.

**There is no single correct JSON error shape.** `scan-capture.js:457` reads `data.error.message`; `inventory-move.js:704` interpolates `${result.error}` and five other clients do `data.error || fallback`. Iteration 1 shipped the string shape and broke the scan UI; iteration 2 shipped the object shape and made batch-move render `Move failed: [object Object]`. Pick by endpoint — the AD-13 object shape for the small set of routes that call `_catalog_json_error`, the legacy string for the rest — and assert the rendered result for one client of each kind.

**Totality still matters, but the surface is far smaller.** The middleware, the hook and the handler all run ahead of every view, so an exception escaping any of them is a 500 with no view involved. Under this design the two iteration-4 escapes are gone structurally rather than by careful guarding: the >4300-digit `Content-Length` is caught by a two-line `except (ValueError, TypeError)` and falls through to the cap (measured: 413, not 500), and the `urlsplit`/`Referer` crash cannot occur because **no code reads `Referer` at all**. What remains: `_cap_for` must swallow every routing exception, and the environ `CONTENT_LENGTH` normalisation must happen before Werkzeug touches it.

**The HTML branch renders, it does not redirect.** Four of pass 4's nine findings came from the same-host referrer logic — the `urlsplit` `ValueError` on `http://[::1`, the `javascript://` scheme bypass, case/port sensitivity, and the `SCRIPT_NAME` self-redirect loop. Rendering `errors/413.html` with a 413 status deletes all four at once, along with `_same_host_referrer`, `_redirects_to_self`, and every acceptance criterion about them. No response target is derived from a request header, so no header can steer it. The cost is real but small: an attachment uploader gets an error page instead of bouncing back to the product page. Note this also diverges from the sibling handlers in `create_error_handlers`, which flash-and-redirect to the index — that is deliberate, and worth a comment, because a redirect answering a rejected POST discards the error context and was itself the self-redirect hazard.

Supporting facts, verified against the installed Flask 3.1.3 / Werkzeug 3.1.8: `flask/wrappers.py` defines `Request.max_content_length` as a property returning `current_app.config['MAX_CONTENT_LENGTH']` absent a per-request override (which is why the config key alone controls the truncation branch); and `request.get_json(silent=True)` does not swallow the 413, because `werkzeug/wrappers/request.py` calls `get_data()` outside the `try` that `silent` guards.

**A startup warning that fires on the shipped defaults is not a diagnostic.** Iteration 4 added a `validate_limits` warning whenever the global body limit exceeded `MAX_FORM_MEMORY_SIZE`. The shipped defaults are 1048576 > 500000, so it fires on **every boot of an unmodified deployment** — and a test asserted that it does. The deployment guide tells operators to aggregate this JSON log; an unconditional WARNING in the out-of-the-box configuration is exactly the noise that trains them to filter the channel, taking the mis-set-ceiling warning (which is a real diagnostic) with it. The information is worth keeping, but it belongs in the documentation and at most at INFO, or the warning must be conditioned on something an operator actually did — e.g. only when `MAX_REQUEST_BODY_BYTES` was overridden from the environment. Do not "fix" this by lowering `MAX_REQUEST_BODY_BYTES` to 500000 or by raising `MAX_FORM_MEMORY_SIZE`; both are pinned elsewhere in this spec.

**The lazy service-limit import does not buy what its comment claims.** Importing `PhotoService` and `ATTACHMENT_MAX_SIZE` inside `validate_limits` was specified to keep PIL, PyMuPDF and the ORM out of `import app`. It does — verified, `import app` loads none of them — but `validate_limits` runs from `init_request_limits`, which runs inside `create_app`, so **every process that builds the app loads all three anyway**: verified, `create_app(TestConfig)` pulls in `PIL`, `pymupdf`/`fitz` and the ORM. `app/main/routes.py` has thirteen in-function `photo_service` imports placed deliberately to avoid this cost. Two integers do not justify defeating them. Keep the imports out of module scope (the circular-import reason is still valid and independent), but obtain the two floors without importing those modules at app-build time — read them lazily only when a floor could actually be breached, or source the constants from a leaf module.

**The ceiling is a two-way knob.** `validate_limits` must hard-fail only on `MAX_UPLOAD_BODY_BYTES <= MAX_REQUEST_BODY_BYTES` (incoherent) and warn — not refuse — when it sits below `PhotoService.MAX_FILE_SIZE` or `ATTACHMENT_MAX_SIZE`. A deployer who wants a stricter posture than 20 MiB on the unauthenticated, `@csrf.exempt`, read-fully-into-memory photo endpoint must be able to choose it; refusing to boot turns a security control into a floor on exposure.

**Values.** 1 MiB global (the largest legitimate non-upload body is a batch `POST /api/inventory/items` or a product form; both are orders of magnitude under it) and 24 MiB for uploads. A body at exactly `PhotoService.MAX_FILE_SIZE` is larger than 20 MiB on the wire once multipart boundaries and part headers are counted, which is why the ceiling is not 20 MiB exactly. Both are env-tunable, hence the startup validation — a mis-set ceiling would otherwise 413 every photo with no diagnostic.

**Residual exposure to record in the config comment.** `main.upload_photo` stays unauthenticated, `@csrf.exempt`, and reads its file fully into memory, now formally sanctioned up to 24 MiB. Rate limiting is out of scope (a closed ledger entry names this bound as the proportionate mitigation), so say so rather than implying uploads are now bounded in aggregate.
