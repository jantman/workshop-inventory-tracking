## Intent

**Problem:** FR36's routing loop stops at the classifier. Story 4.2 shipped the pure `classify()` (`app/utils/scan_router.py:228`) and the frozen `ScanClassification` (`app/models.py:455`), but nothing in the app calls them: there is no `resolve_scan()`, no `ScanResolution`, and no free-text search at all. AD-16's config flow — the service reading `GS1_INTERNAL_AI`/`GS1_INTERNAL_TOKEN` and passing them into the pure function — is unproven in production code (`4-2-pure-scan-classifier.md:236`). A scan therefore cannot become a product, and Stories 4.4/4.5 and Epics 7/8/9 are all blocked on the second of AD-15's two frozen shapes and on AD-17's single search entrypoint.

**Approach:** Add `ScanResolution` to `app/models.py` (AD-15's three fields: `classification`, `product`, `free_text_hits`), and two public read-only methods to `CatalogService`: `resolve_scan(raw)`, which reads the config pair, calls `classify()`, looks up the matched Product for an `internal` or `gtin` classification, and falls through to search when nothing matches; and `search_products(query, filters)`, the AD-17 sole free-text entrypoint over identifier values, description, notes, manufacturer and MPN, built on the simplest thing that satisfies the fallthrough (case-folded substring `LIKE`, deterministic order, bounded result count) behind a signature Epic 8 will reuse without changing call sites.

## Boundaries & Constraints

**Always:**
- `ScanResolution` is `@dataclass(frozen=True)` in `app/models.py` with exactly AD-15's three fields in AD-15's order — `classification: ScanClassification`, `product`, `free_text_hits` — all required, no defaults, matching the posture `ScanClassification` already sets. `app/models.py` stays a **leaf module** (it imports nothing from `app/`, pinned by `test_models_stays_a_leaf_module`), so `product` cannot be annotated or `isinstance`-checked against `app.database.Product`; it is annotated loosely and the docstring says what it actually holds and why the check is absent.
- `__post_init__` follows the house error taxonomy that `ScanClassification.__post_init__` (`app/models.py:545-620`) settled over three review passes: **type checks before combination checks**, `TypeError` for a wrong type, `ValueError` for an illegal combination, messages naming the field and `type(x).__name__`, and `object.__setattr__` for normalization. `free_text_hits` is copied into a `tuple` unconditionally (the aliasing lesson of `ecia_fields`), a `str`/`bytes`/`Mapping` is rejected rather than exploded into elements (the coercion lesson), and `product`-set-with-hits-non-empty is a `ValueError` — a resolution cannot both match and fall through.
- `resolve_scan` is the **AD-16 config seam**, and it mirrors `encode_internal_payload` (`app/mariadb_catalog_service.py:1684-1686`) exactly: `Config.GS1_INTERNAL_AI` / `Config.GS1_INTERNAL_TOKEN` read from the `Config` class **inside the method body on every call**, never captured at import or cached on `self`, passed as keyword args `ai=`/`token=` into `classify()`. No literal `'96'`/`'WIT'` anywhere in the new code or its tests.
- `raw` reaching `resolve_scan` is **already cleaned** by the caller, the same contract `classify()` states (`app/utils/scan_router.py:82-89`). The service does no trimming, no length bound, and no whitespace handling of its own — `MAX_SCAN_LENGTH`/`_SCAN_TRIM`/`_clean_scan_input` stay where they are.
- Text that gets *used* is AIM-stripped first, via the exported `strip_aim_prefix()` (`app/utils/scan_router.py:175`), never re-derived — `classification.raw` deliberately still carries the prefix.
- Per-kind resolution, exhaustive over the four kinds:
  - `internal` → look up `Product.internal_id == classification.normalized_value` (AD-3: `internal_id` is the scan-lookup business key). Miss → search on `normalized_value`.
  - `gtin` → look up a `ProductIdentifier` row with `identifier_type == IdentifierType.GTIN.value` and `value == classification.normalized_value`, which is already the canonical 14-digit key (AD-7: lookup is against the normalized-14 namespace; `GTIN_UNVALIDATED` is outside it and is never matched by this arm). Miss → search on `strip_aim_prefix(raw)`, the digits as scanned.
  - `free_text` → no lookup; search on `strip_aim_prefix(raw)`.
  - `ecia` → no lookup and **no search**: `product=None`, `free_text_hits=()`. Story 4.4 owns this arm.
- `resolve_scan` never raises on any `str` `raw` given a valid configured grammar (NFR8, inherited from `classify`). Exactly three exceptions are reachable, all of them faults of the caller or the deployment, and all tested: `TypeError` from `classify` for a non-`str` `raw`; `gs1.InvalidGs1PayloadError` propagated **unchanged** for a malformed configured grammar; and whatever the DB raises, which read methods deliberately do not swallow (`app/mariadb_catalog_service.py:128-131`).
- `search_products(query, filters=None, *, limit=...)` is AD-17's **sole** free-text implementation. It covers `ProductIdentifier.value` (every identifier type, via an `EXISTS` correlated subquery — there is no `Product.identifiers` relationship and a join would duplicate rows), `Product.internal_id`, `Product.description`, `Product.notes`, `Product.manufacturer`, `Product.mpn`. Case-folded substring matching via `func.lower(col).like('%…%', escape='\\')` so SQLite and MariaDB agree (`app/database.py:1084-1088`); user wildcards escaped; result count bounded and order deterministic.
- The `filters` parameter exists so AD-17's entrypoint is fixed now and Epic 8 changes no call sites, but this story implements **no** filter: `None` and an empty mapping mean "no filters"; any non-empty `filters` raises `NotImplementedError` naming the keys and Story 8.2, matching the file's dispatch convention (`app/mariadb_catalog_service.py:380, 477`). Silently ignoring filters would hand a caller unfiltered rows it believes are filtered.
- Both methods are **read-only**: `session = self.Session()` outside the `try`, `try: … finally: session.close()`, no commit, no rollback, no `except`, no audit log — the exact shape of `get_identifiers_for_product` (`app/mariadb_catalog_service.py:1654-1663`). Because nothing commits, scalar columns of returned rows stay readable after the session closes; **relationship attributes must never be touched** on them (`DetachedInstanceError`, documented at `:128-137` and `:1186-1188`), and both docstrings must say so.
- New tests are `tests/unit/test_scan_resolution.py`, `@pytest.mark.unit` on each method, `class Test*`, using the real SQLite `catalog_service` fixture idiom of `tests/unit/test_catalog_service.py:13-15` with products created through `create_product()` — no mocks. Docstrings cite FR36/AD-15/AD-16/AD-17/AD-7/NFR8.

## Design Notes

**Why the route is still not wired.** Story 4.2 predicted 4.3 would replace `outcome: 'unrouted'`. It should not, for the same reason 4.2 declined: an outcome without a destination routes nowhere. Story 4.5 — "Scan outcome routing in the UI" — owns the destinations (FR40's pre-filled create form, FR39's distributor pre-fill, FR41's add-a-purchase offer), and the response shape is a function of those destinations, so anything invented here is redesigned one story later. 4.3's ACs (`epics.md:464-470`) name only `resolve_scan` and `search_products`; the epic's own dependency line puts UI routing in 4.5 (`epic-4-context.md:50`). Concretely, wiring it now would rewrite five unit tests (`test_happy_path_echoes_raw_unrouted`, `test_raw_is_echoed_byte_for_byte`, `test_endpoint_constructs_no_catalog_service`, `test_response_has_no_resolution_fields`, and the logging assertion on `outcome=unrouted`) plus one e2e test (`tests/e2e/test_wedge_scan.py:119`) against a contract 4.5 rewrites again.

**Why three ledger entries that name this story stay open.** `:145` (the CSRF exemption) and `:137` (at-least-once scan transport) are both explicitly gated on `/api/scan` gaining **side effects**. It gains none here: the endpoint is untouched, and both new methods are read-only — no commit, no audit log, no mutation — so resolution is idempotent by construction. Both entries remain correctly aimed at 4.5. `:133` (relocating `_SCAN_TRIM`/`_clean_scan_input`/`MAX_SCAN_LENGTH` out of `routes.py`) is aimed here on the assumption 4.3 becomes the second Python consumer of the trim rule. It does not: `resolve_scan` takes already-cleaned text, exactly as `classify()` does, because a service that re-cleans its input would be the third copy of the rule rather than a shared one. The entry now correctly aims at 4.5, which is the story where the route calls the cleaner *and* the resolver.

**Why `find_product_id_by_gtin` is not reused for the GTIN arm.** It takes an unnormalized value and re-runs `gtin.normalize_gtin` on a `normalized_value` the classifier already normalized, returns an id rather than a row, and opens its own session — so reusing it costs three sessions per scan on top of the per-request-engine problem the ledger already records at `:5`. `resolve_scan` queries the same namespace inline instead. The duplication that buys is exactly one filter pair, and `TestNamespaceAgreement` pins the two against drift.

**Why the fallthrough query differs per kind.** `internal` searches `normalized_value` (the bare token-stripped id, which is what `products.internal_id` and the mirrored identifier row actually store — the `96WIT` prefix is an encoding artifact present in no column). `gtin` searches the AIM-stripped raw digits instead: the normalized-14 namespace was already searched exactly by the lookup arm, so re-searching it adds nothing, while the scanned form can substring-match a `GTIN_UNVALIDATED` row stored as typed. `free_text` searches the AIM-stripped raw. `ecia` searches nothing.

**Why `ecia` resolves to nothing rather than searching the envelope.** FR36 sends a format-06 envelope to the ECIA parser, which does not exist until Story 4.4. Searching the raw envelope — control characters, record separators and all — is a query with no meaning that 4.4 would immediately replace with a lookup on the parsed `1P`/`P`. Returning `product=None, free_text_hits=()` is honest and still lands the operator somewhere (4.5 renders the raw scan for manual handling, NFR8). 4.4 owns filling this arm in.

**Shape sketch** (the taxonomy, not the docstrings):

```python
@dataclass(frozen=True)
class ScanResolution:
    classification: ScanClassification
    product: Optional[Any]          # a detached app.database.Product; see docstring
    free_text_hits: Tuple[Any, ...]

    def __post_init__(self):
        if not isinstance(self.classification, ScanClassification):
            raise TypeError(...)                      # type before combination
        hits = self.free_text_hits
        if isinstance(hits, (str, bytes, bytearray, Mapping)):
            raise TypeError(...)                      # not a sequence of products
        object.__setattr__(self, 'free_text_hits', tuple(hits))   # copy, always
        if self.product is not None and self.free_text_hits:
            raise ValueError(...)                     # matched *and* fell through
```
