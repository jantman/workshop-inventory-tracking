## Intent

**Problem:** AI `01` in a GS1-128 or GS1 DataMatrix is the most common way a manufacturer encodes a GTIN on a box, and this system classifies every form of it as `free_text`. Verified on this checkout: `classify('0109506000134352')`, `classify(']d20109506000134352')` and `classify('\x1d0109506000134352')` all return `kind=free_text, normalized_value=None`, while the bare `'9506000134352'` inside them is a valid EAN-13 that resolves `gtin` with key `'09506000134352'`. That is spec-conformant — FR36 has exactly four rules and none of them reads an element string that is not the internal one — so a whole class of real barcode degrades to a text search, against FR36's stated purpose that any barcode in the shop resolves from one wedge scan.

**Approach:** Add a fifth FR36 rule between the ECIA envelope and the bare-GTIN rule. `app/utils/gs1.py` — already the single source of truth for GS1 element-string grammar — gains a sibling to `decode` that recognizes a payload opening with AI `01` and returns the 14-digit trade item number it carries, verbatim and unjudged. `scan_router.classify()` calls it and, on a hit, hands the extracted digits to the **existing** `gtin` arm, so the number is normalized, check-digit validated and all-zero-refused by exactly the code a bare GTIN goes through and produces exactly the same `ScanClassification`. `ScanKind`, `ScanClassification`, `resolve_scan` and every UI surface are untouched: an AI-01 scan simply *is* a `gtin` scan from the moment it leaves the classifier.

## Boundaries & Constraints

**Always:**
- FR36's precedence becomes five rules, first match wins, rule 5 always matches: (1) internal element string; (2) ISO/IEC 15434 format-06 envelope carrying at least one recognized identifier; (3) a GS1 element string opening with AI `01` → its trade item number becomes the value rule 4 judges; (4) a check-digit-valid trade item number → `GTIN`; (5) anything else → `FREE_TEXT`.
- Rules 3 and 4 share **one** `gtin` arm and therefore one `gtin.normalize_gtin` call. The extracted digits are not validated, padded, or judged inside `gs1.py` or `scan_router.py` — accepted lengths, the mod-10 check and the all-zero refusal (DW-69) stay behind `normalize_gtin`, and an AI-01 payload whose number fails any of them falls through to `FREE_TEXT` with no code of its own (AD-16).
- The element-string parsing lives in `app/utils/gs1.py`. `scan_router.py` must contain no `'01'` literal, no AI table, and no element-string field arithmetic — it calls one function and reads its answer, exactly as rule 1 delegates to `gs1.decode`, rule 2 to `ecia`, and rule 4 to `gtin` (AD-16).
- AI `01` is predefined-length (`n2+n14`) per the GS1 General Specifications: the element string is exactly `01` + 14 digits, no FNC1 separator terminates it, and the next element string abuts it directly. Recognition therefore requires exactly 14 ASCII digits after `01`, and what follows must be another element string — a GS, an ASCII digit (every AI opens with one), or end of input. A non-digit, non-GS tail means the string only *resembles* an element string and is not one.
- Transmission tolerance mirrors `gs1.decode` exactly — `raw.strip()`, then one optional leading FNC1 — because both functions recognize element strings arriving from the same symbologies through the same wedge. This widens the whitespace asymmetry `scan_router`'s docstring and `TestWhitespaceAsymmetryBetweenRules` already document (rules delegated to `gs1` tolerate padding; rules judged in `scan_router` do not) from one rule to two. Update both to say so.
- `gs1.py` stays PURE (standard library only) and keeps its NFR8 contract: the new function never raises on any `raw` whatsoever, including a non-`str` — it returns `None`. It reads no configuration: AI `01` is assigned by GS1, not by this deployment, so it is a module constant and takes no `ai`/`token` argument.
- `classify()` still never raises on a `str` `raw` (NFR8) and still returns `raw` verbatim, AIM prefix and all.
- An AIM-prefixed AI-01 payload (`']d1' + '01…'`, `']C1' + '01…'`) works because `strip_aim_prefix` already runs before every rule. No AIM handling is added.
- Amend the frozen precedence everywhere it is written down: PRD FR36 and its testable consequences, `epics.md` (the FR list and Story 4.2's acceptance criteria), the PRD addendum's Epic 4 story list, `docs/user-manual.md`'s numbered "What Happens to a Scan" list, and the Story 4.2 spec's Always list, I/O matrix and residual-risk line. Amendments state the new rule; they do not rewrite history.
- New tests go in `tests/unit/test_gs1.py` (the recognizer, exhaustively) and `tests/unit/test_scan_router.py` (a new `TestTradeItemElementString` class), `@pytest.mark.unit`, `Test*` classes, the house one-case-per-line parametrize idiom with an aligned trailing `#` saying why the case exists, fixture-free, citing FR36/FR37/FR37a/AD-16/NFR8.
- Every I/O-matrix row of Story 4.2 that is not an AI-01 form must classify exactly as it does today. `'0109506000134352'` moves out of `test_every_rejection_reason_falls_through_to_free_text` (`tests/unit/test_scan_router.py:330`) and into the new class; nothing else in that parametrize list may move.

Only a payload *opening* with AI 01 is read, and only its one fixed-length field.

## Design Notes

**Why a sibling function rather than a change to `decode`.** The ledger says to "extend `gs1.decode`'s foreign-payload handling". The requirement that phrase carries is *where the parsing lives* — in the module that owns GS1 element strings, not re-derived in `scan_router`. Extending `decode` itself cannot mean widening its return type: `Optional[InternalPayload]` is a frozen Story 2.4/2.5 contract whose `internal_id`/`ai`/`token` fields are meaningless for AI 01, and `tests/unit/test_gs1.py` pins that AI-01 vectors decode to `None` precisely so a foreign payload can never be mistaken for one of ours. A sibling honours the intent and keeps that boundary machine-checked.

**Why rules 3 and 4 share one arm.** The intent is "hands it to the existing `gtin` arm so it resolves exactly as a bare GTIN does". The cheapest way to make "exactly" true is to have one arm:

```python
trade_item = gs1.decode_trade_item_number(candidate)     # rule 3
gtin_candidate = candidate if trade_item is None else trade_item
if gtin_candidate.isascii() and gtin_candidate.isdigit():   # rule 4
    try:
        return ScanClassification(kind=ScanKind.GTIN,
                                  normalized_value=gtin.normalize_gtin(gtin_candidate),
                                  ecia_fields=None, raw=raw)
    except gtin.InvalidGtinError:
        pass                                              # -> rule 5
```

Two arms would be two places for the check digit, the all-zero refusal and the 14-digit key to drift apart — the duplication AD-16 exists to prevent — and would make the AI-01 path's inheritance of DW-69 a coincidence rather than a structural fact.

**Why the tail must be a digit, a GS, or nothing.** AI 01 is predefined-length, so nothing delimits it: on a real label `01<14>` is followed directly by the next AI, which always opens with a digit, or by a GS, or by the end of the scan. Accepting an arbitrary tail would make `'0109506000134352 RES 10K 0805'` a GTIN scan; accepting only end-of-string would reject the extremely common `01`+`17`+`10` concatenation that `tests/unit/test_gs1.py:387` already carries as a realistic vector. The digit-or-GS-or-nothing rule is the one that admits every legal element-string chain and no free text.

**How that rule was sharpened during review, and why the contract still reads as it does.** The intent contract states the tail rule as "a GS, an ASCII digit (every AI opens with one), or end of input", and the shipped code is stricter than that sentence twice over. Both are the same reading of the requirement the sentence exists to serve — *what follows must be another element string* — carried through to the two places one digit was not enough:

- **Two digits, not one.** Every GS1 AI is two to four digits, so `'…1343521 RES 10K'` is free text with a lucky sixteen-character prefix and `'…13435217'` is an AI. `_MIN_AI_LENGTH = 2` in `app/utils/gs1.py` is the operative constant; the first review pass found the one-character form admitting free text and tightened it.
- **The GS is a separator, not an exemption.** What follows a transmitted GS is itself an element string, so it is held to the same two-digit opener test. Testing only the abutted side left `'01<gtin>\x1dRES 10K 0805'` reading as a trade item number; the second review pass closed it.
- **Exactly one GS, and only on the tail.** Consuming one separator means a doubled GS leaves a GS as the opener and the scan is refused, which is right — a doubled GS encloses an empty element string the grammar does not permit — but it is *not* symmetric with the leading side, where `str.strip()` absorbs any number. The third review pass found the asymmetry undocumented and unpinned rather than wrong; it is now stated in the docstring and pinned from both ends by `test_the_leading_side_absorbs_separators_the_tail_does_not`.

The contract sentence is left as written because amendments state the new rule rather than rewrite history, and because nothing it *requires* was contradicted — the code refuses a strict subset of what the sentence's letter would admit, and every row of the I/O matrix classifies as the matrix says. A future implementer reading the contract should take this note, `_MIN_AI_LENGTH`'s comment, and `TestDecodeTradeItemNumber` as the operative statement of the rule; relaxing either tightening re-opens a defect that has been found twice.

**Why no existing vector can move.** An AI-01 match needs at least 16 characters (`'01'` + 14 digits). Every length rule 4 accepts is 8, 12, 13 or 14. The two candidate sets are disjoint, so rule 3 cannot steal a bare GTIN, and it cannot steal an envelope (rule 2 runs first and an envelope opens `'[)>'`) or an internal label (rule 1 runs first). The only inputs whose classification changes are the ones this work exists to change.
