## Intent

**Problem:** FR38 is unimplemented and the epic's last scan kind is inert. Story 4.2 recognizes the ISO/IEC 15434 format-06 *header* and stops (`app/utils/scan_router.py:204-225`, `:46-49`), so `ScanClassification.ecia_fields` is `None` for every scan the shipped classifier can produce, and Story 4.3's `resolve_scan` answers an envelope with `product=None, free_text_hits=()` and issues no query at all (`app/mariadb_catalog_service.py:2235-2238`), documented there as "Story 4.4 owns this arm". Scanning a DigiKey or Mouser package therefore does nothing: nothing is extracted, nothing is looked up, and Story 4.5 has no `P`/`1P`/`Q`/`K`/`1K`/`9D`/`10D` to pre-fill a create form with (FR39). NFR8's other half is also unbuilt — a *valid* header wrapping unparseable contents currently classifies `ecia` and hands 4.5 an envelope it cannot use, where the architecture says it must degrade to `free_text` carrying the raw scan (AD-5).

**Approach:** Add a pure `app/utils/ecia.py` that owns the format-06 grammar — the header (moved out of `scan_router`, so one module holds it), envelope recognition, and extraction of the seven AD-15 data identifiers from the GS-delimited records. `scan_router` rule 2 delegates to it exactly as rule 1 delegates to `gs1.decode()` (AD-16's posture, AD-4's module pattern): an envelope that yields at least one recognized field classifies `ecia` carrying those fields, and one that yields nothing falls through to rule 4 (NFR8). Then fill in `resolve_scan`'s `ecia` arm: an exact, case-folded lookup of the parsed part numbers against the two places a manufacturer part number lives, falling through to `search_products()` on a miss or an ambiguity, so the last of FR36's four kinds stops dead-ending.

## Boundaries & Constraints

**Always:**
- `app/utils/ecia.py` is a **pure module** on the AD-4 pattern (`gtin.py`, `gs1.py`, `internal_id.py`, `category.py`): standard library only — no Flask, no config, no SQLAlchemy, no I/O, and **no import of `app.models` or `app.utils.scan_router`**, so the dependency runs one way (`scan_router` → `ecia`) and cannot cycle.
- It is the **single source of truth for the format-06 grammar**. `_ECIA_HEADER` and `_ECIA_SEPARATORS` move out of `app/utils/scan_router.py:112-121` and `_is_ecia_envelope` (`:204-225`) moves with them, becoming public `ecia.is_envelope()`; its existing docstring reasoning (why the header alone is judged, why an undelimited indicator is not an envelope) moves verbatim rather than being re-derived. After this story the literal `[)>` appears in exactly one module under `app/`.
- Two public functions, both of which **never raise on a `str`** (NFR8) and both of which raise `TypeError` for a non-`str` — a caller fault, matching the door `classify()` already keeps (`app/utils/scan_router.py:283-286`). The message names the field and `type(x).__name__` and does **not** interpolate the value, so no bounded-repr helper is duplicated from `scan_router`:
  - `is_envelope(value) -> bool` — header recognition, unchanged in behavior from `_is_ecia_envelope`.
  - `parse_fields(value) -> Dict[str, str]` — a **fresh, plain, mutable dict** on every call (the caller owns it; `ScanClassification.__post_init__` copies and proxies it, so no shared state escapes). `{}` for anything that is not an envelope and for an envelope carrying nothing recognized.
- The extraction grammar, stated once and tested exhaustively:
  - The message body is `value` after the header, truncated at the **first RS (`\x1e`)** — per ISO/IEC 15434 the RS after the data terminates format 06, and what follows is a different format or the `RS EOT` trailer. Anything after it is not this message's data.
  - The body splits on **GS (`\x1d`)**; empty elements (a leading GS after the header, the trailing GS the canonical vector carries) are skipped.
  - A data identifier is `<optional digits><one uppercase ASCII letter>` at the start of an element; the rest of the element is the value, **verbatim** — no trimming, no case folding, no type coercion. An element that does not open with that shape is ignored.
  - Only the seven AD-15 keys are kept — `P`, `1P`, `Q`, `K`, `1K`, `9D`, `10D`, declared once as a module constant. FR38 says "at minimum", so any other legal MH10.8.2 identifier (`1T`, `4L`, `30P`, …) is ignored silently rather than being an error.
  - A recognized identifier with an **empty value** contributes nothing and is omitted — there is nothing to pre-fill or look up.
  - A repeated identifier keeps its **first** occurrence. Deterministic, and it preserves the leading record of a label that repeats one.
  - No date parsing and no quantity coercion. `9D`/`10D` are `YYWW` per the PRD addendum and `Q` is a count, but the frozen field type is `Mapping[str, str]` (`app/models.py:542`), so values stay strings and interpretation belongs to the consumer (4.5, Epic 7).
- `scan_router.classify()` rule 2 becomes a delegation with an explicit degradation: if `ecia.is_envelope(candidate)` and `ecia.parse_fields(candidate)` is non-empty → `ScanClassification(kind=ECIA, normalized_value=None, ecia_fields=<the dict>, raw=raw)`; otherwise **fall through to rules 3 and 4**, which lands a header-only or garbage-bodied envelope on `FREE_TEXT` carrying the raw scan (AD-5, NFR8). The precedence order, rules 1/3/4, `strip_aim_prefix`, the AIM handling and `raw` staying verbatim are all unchanged; the parse runs on the AIM-stripped candidate, so `']d1' + envelope` parses identically.
- Because the classifier is the only producer, `kind is ECIA` now implies `ecia_fields` is a non-empty mapping. Consumers still read it defensively (`classification.ecia_fields or {}`), since `ScanClassification` itself permits `ECIA` with `None`.
- `resolve_scan`'s `ecia` arm (`app/mariadb_catalog_service.py:2235-2238`) is replaced by a lookup that follows the shape the `internal` and `gtin` arms already have — open a session only for the lookup, `try/finally: session.close()`, no commit, no audit log, then join the shared fallthrough tail:
  - Candidate part numbers, in order: `1P` (the supplier part number, required per the ECIA spec), then `P`. Only non-empty ones. The arm deliberately does **not** depend on which of the two a given distributor puts the manufacturer part number in — it tries both.
  - One query, one session: an exact, case-folded (`func.lower(col) == value.lower()`, matching `search_products`' explicit fold) match of any candidate against `Product.mpn` **or** an `EXISTS` correlated subquery on a `ProductIdentifier` row with `identifier_type == IdentifierType.MPN.value` — `EXISTS` rather than a join, for the same reason `search_products` uses it (a product matching twice must appear once, without a SQL `DISTINCT`). Ordered by `Product.id.asc()`, `.limit(2)`.
  - Exactly one match → `product`. **Zero or more than one → no product**, and the fallthrough search runs: `mpn` is not unique, so silently returning the oldest of several would answer a question nobody asked. `search_products` covers `mpn`, so the ambiguous set comes back as `free_text_hits` and Story 4.5 renders a choice.
  - The fallthrough text is the first candidate. **No part-number identifier at all** (an envelope carrying only `Q`/`K`/`9D`) → no lookup, no search, `product=None, free_text_hits=()`: a legal terminal state, since there is nothing a part-number search could mean. `VENDOR_SKU` identifier rows are deliberately outside the lookup — see Design Notes.
- Every docstring that this story falsifies is corrected in the same commit: `app/models.py` (`ScanClassification`'s "Always `None` in Story 4.2" and the `ScanKind.ECIA` member note), `app/utils/scan_router.py`'s module contract ("No ECIA field parsing"), and `resolve_scan`'s per-arm list, session-count rule and "Story 4.4 owns this arm".
- Tests: a new exhaustive `tests/unit/test_ecia.py` for the pure module (AD-4 requires it); the ECIA cases in `tests/unit/test_scan_router.py` updated for the new rule-2 outcome; and `TestEciaIsStoryFourFour` in `tests/unit/test_scan_resolution.py` replaced by a real ECIA-arm suite. `@pytest.mark.unit` on every test, `Test*` classes, the existing `catalog_service`/`product` fixtures and `create_product()`, no mocks of the service or the ORM. Docstrings cite FR36/FR38/FR39/NFR8/AD-4/AD-5/AD-15.

**Never:**

A missing RS/GS (deferred-work `:164`) or a *leading* separator before the header (deferred-work `:173`) still routes to `free_text`; inventing tolerance requires the physical scanner and belongs to the story that owns the caller seam. Both entries stay open and stay aimed at 4.5.

Nothing under `app/main/`, `app/templates/`, `app/static/`, `tests/e2e/`, `migrations/` or `docs/images/` is touched, so no screenshot goes stale.

- `tests/unit/test_gs1.py` and `tests/unit/test_scan_routes.py` are not edited; both must stay green untouched.

## I/O & Edge-Case Matrix

Vectors use the repo's canonical names: `ECIA_SHORT = '[)>\x1e06\x1dP123\x1e\x04'`, `ECIA_FULL = '[)>\x1e06\x1dP12345\x1d1PABC\x1dQ10\x1d\x1e\x04'`.

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Canonical vector (FR38) | `parse_fields(ECIA_FULL)` | `{'P': '12345', '1P': 'ABC', 'Q': '10'}` — trailing GS and `RS EOT` trailer consumed | No error expected |
| All seven identifiers | `'[)>\x1e06\x1dP1\x1d1P2\x1dQ3\x1dK4\x1d1K5\x1d9D6\x1d10D7\x1e\x04'` | All seven AD-15 keys, each with its own value | No error expected |
| Unrecognized identifiers ignored | `'[)>\x1e06\x1d1PABC\x1d1TLOT9\x1d4LUS\x1e\x04'` | `{'1P': 'ABC'}` — FR38 is a minimum, not a whitelist violation | No error expected |
| No trailer | `'[)>\x1e06\x1dP123'` | `{'P': '123'}` | No error expected |
| Data after the first RS | `'[)>\x1e06\x1dP1\x1e07\x1d1PX\x1e\x04'` | `{'P': '1'}` — a second format is not this message's data | No error expected |
| Empty value omitted | `'[)>\x1e06\x1dQ\x1e\x04'` | `{}` | No error expected |
| Duplicate identifier | `'[)>\x1e06\x1dP1\x1dP2\x1e\x04'` | `{'P': '1'}` — first occurrence wins | No error expected |
| Value kept verbatim | `'[)>\x1e06\x1d1P rc0805 \x1e\x04'` | `{'1P': ' rc0805 '}` — spaces and case preserved | No error expected |
| Lowercase identifier | `'[)>\x1e06\x1dp123\x1e\x04'` | `{}` — MH10.8.2 identifiers are uppercase | No error expected |
| Not an envelope | `parse_fields('RES 10K')`, `''`, `'[)>\x1e05\x1dP1'`, `' ' + ECIA_SHORT` | `{}` in every case | No error expected |
| Non-`str` | `parse_fields(b'[)>')`, `is_envelope(None)` | — | `TypeError` naming the type; the value is not interpolated |
| Hostile input (NFR8) | 4096 chars of C0 controls, `'[)>' * 50`, `'\x1d' * 50`, a lone surrogate, `'[)>\x1e06\x1d' + '\x00' * 100` | A `dict` every time | Never raises |
| Classifier: envelope with fields | `classify(ECIA_FULL, ai=…, token=…)` | `kind=ECIA`, `ecia_fields == parse_fields(ECIA_FULL)`, `normalized_value is None`, `raw` verbatim | No error expected |
| Classifier: behind an AIM prefix | `']d1' + ECIA_FULL` | Same fields as the bare vector; `raw` still starts `']d1'` | No error expected |
| Classifier: degradation (NFR8) | `'[)>\x1e06'`, `'[)>\x1e06\x1e'`, `'[)>\x1e06\x1d!!!garbage!!!'` | `kind=FREE_TEXT`, `ecia_fields is None`, `raw` verbatim — was `ECIA` before this story | No error expected |
| Classifier: other kinds unchanged | internal / GTIN / free-text vectors | `ecia_fields is None`; kinds and normalized values unchanged from `035f226` | No error expected |
| Service: hit on the `mpn` column | Product with `mpn='ABC'`; `resolve_scan(ECIA_FULL)` | `kind=ECIA`, `product` is that product, `free_text_hits == ()` | No error expected |
| Service: hit on an MPN identifier row | Product with no `mpn` but an `MPN` identifier `'ABC'` | Same result — both places are searched | No error expected |
| Service: hit via `P` when `1P` misses | `1P` matches nothing, `P='12345'` matches a product | Resolves to that product | No error expected |
| Service: case-folded exact match | Stored `mpn='abc'`, label carries `1PABC` | Resolves to that product (ASCII fold, as `search_products` folds) | No error expected |
| Service: exact, not substring | Stored `mpn='ABCDEF'`, label carries `1PABC` | `product is None`; the product appears in `free_text_hits` via the search | No error expected |
| Service: ambiguous | Two products both `mpn='ABC'` | `product is None`; both in `free_text_hits`, id-ascending | No error expected |
| Service: miss falls through (FR36) | No product matches `'ABC'` | `product is None`, `free_text_hits` = `search_products('ABC')` — searched on the part number, not the raw envelope | No error expected |
| Service: no part-number identifier | `'[)>\x1e06\x1dQ10\x1d9D2612\x1e\x04'` | `kind=ECIA`, `product is None`, `free_text_hits == ()`, and **no query issued** | No error expected |
| Service: degraded envelope | `resolve_scan('[)>\x1e06\x1d!!!garbage!!!')` | `kind=FREE_TEXT`; searches the AIM-stripped raw; lands somewhere, never an error (NFR8) | No error expected |
| Service: hostile envelopes | Envelope vectors carrying NUL / lone surrogate / 4096 chars | A `ScanResolution` every time; never "every product" | Never raises |

## Design Notes

**Why a new module rather than more of `scan_router.py`.** AD-4 names the pattern — pure functions in `app/utils/`, "each its own single source of truth" — and the epic already runs on it: rule 1's recognition is delegated whole to `gs1.decode()` and rule 3's arithmetic to `gtin.py`, precisely so `scan_router` owns *precedence* and nothing else. Rule 2 was the only rule whose grammar lived inside the router, and only because there was no grammar yet — just a header check. Adding a record parser there would make the one module that must stay readable as four rules into the one module that also implements MH10.8.2. The architecture's capability map (`ARCHITECTURE-SPINE.md:279`) names `utils/scan_router.py` for Epic 4 but names no ECIA module either way; it lists touchpoints, not a file whitelist, and AD-4's rule is the one that speaks to placement.

**Why the header moves rather than being copied.** A second copy of `'[)>\x1e06'` is exactly the defect this repo keeps finding in itself — three copies of the scan trim rule (deferred-work `:134`), two LIKE escapers (`:51`, fixed in 4.3). The parser cannot skip the header without knowing it, so either the router imports the constant from the parser or both hold it. Moving recognition with it makes `ecia.py` answer both questions about an envelope and leaves the router asking, not deciding.

**Why a degraded envelope becomes `free_text` rather than `ecia` with no fields.** AD-5 states it directly: "on a malformed/unrecognized format-06 envelope it classifies as `free_text` carrying the raw scan and never raises (satisfies NFR8)", and Story 4.2's own module contract predicted "a valid header with unparseable contents degrades back to free text" as 4.4's job (`app/utils/scan_router.py:46-49`). The alternative — `ecia` with `ecia_fields={}` — would hand Story 4.5 a kind whose entire purpose is pre-filling a form, with nothing to pre-fill, and would leave the operator on a screen that says "distributor label" about a scan nothing could be read from. `free_text` puts the raw scan into a search, which is what "surfaced for manual handling" means everywhere else in this epic. The cost is that three vectors change kind, which is why the change is stated in an AC rather than left to a diff.

**Why the lookup tries `1P` and `P` without deciding which is which.** The PRD addendum defines them by role — "`P` customer part number, `1P` supplier part number (required per spec)" — and which physical number a given distributor prints in each is a property of that distributor's label, not of this system. A rule that hard-codes "`1P` is the MPN" is a guess that fails silently on any label that does it the other way: the scan would resolve to nothing and the operator would create a duplicate product. Trying both against the two places a part number can live is the same answer under either reading, costs one query, and needs no fact this project has not established. `1P` leads only because the spec makes it the required field, and that ordering matters solely for which text the fallthrough searches.

**Why ambiguity falls through instead of picking one.** `products.mpn` is nullable and carries no unique constraint, and `MPN` identifier rows are global-scoped, so two products genuinely can share a part number (a re-order under a second catalog entry, an equivalent part — Epic 10's whole subject). The `internal`/`gtin` arms use `.first()` legitimately: `internal_id` is `UNIQUE` and the GTIN namespace is a key space. Doing the same here would resolve a scan to the oldest of several products, which is a wrong answer rather than a thin one. Falling through returns the same set as hits — `search_products` covers `mpn`, so the exact matches are a subset of the substring matches — and lands 4.5 on a list.

**Why `VENDOR_SKU` rows are outside the lookup.** A distributor part number in `P` is conceptually a vendor SKU, and matching it would resolve more scans. But `VENDOR_SKU` is vendor-scoped (`app/models.py:168-174`): its uniqueness is per vendor, so an unscoped exact match can hit another vendor's identical SKU and resolve a DigiKey label to a product identified by a Mouser number. The scan carries no vendor, and inferring one from the envelope is not something FR38 describes. FR39 names MPN as what a distributor scan pre-fills, so MPN is what it resolves on; the vendor-scoped case needs a vendor seam that does not exist yet.

**Why the four ledger entries that name this story stay open.** `:164` (a wedge may not deliver RS/GS at all) and `:125` (a wedge may not be able to type control characters into a text input) are both hardware questions that need the physical Tera HW0009 and a real DigiKey label; this story cannot answer either, and relaxing the header to tolerate missing separators would invent a transmission form nobody has observed while promoting genuinely damaged scans to `ecia`. `:173` (an *extra* leading separator, which routes an internal label correctly and an envelope to `free_text`) is aimed at "Story 4.3 or 4.4, whichever owns the caller seam" — neither does. The fix is in the cleaner or in the route that calls it, both of which are Story 4.5's; absorbing separators in `classify()` or in `ecia.py` would be the third copy of the trim rule, which is the entry `:134` is about. All four stay open and are re-aimed at 4.5 rather than closed here.

**Where the shipped code deliberately exceeds the contract's literal text.** Three review-driven changes went past what the Always list spells out. None reverses a decision the contract makes; each closes a case the contract's wording did not anticipate, and each is strictly additive — no scan that resolved before resolves differently. Recorded here, outside `<intent-contract>`, because the contract is what Stories 4.5, 7 and 9 are told to read and it should not silently under-describe what shipped.

1. **Candidates are trimmed and de-duplicated.** The contract says "Only non-empty ones." A value that is non-empty but blank (`1P` holding three spaces) is truthy, so it became `candidates[0]` and the fallthrough searched for nothing — dead-ending a label whose `P` was usable. And `search_products` strips its own query, so an untrimmed candidate could only ever miss the exact lookup while the fallthrough silently succeeded. `parse_fields` still keeps values verbatim; the trim lives in the arm, so what 4.5 pre-fills is still what was printed.
2. **An unfolded equality disjunct runs beside the folded one.** The contract prescribes `func.lower(col) == value.lower()`. That alone can never match a non-ASCII part number under SQLite, whose `LOWER()` is ASCII-only while Python's `str.lower()` is not — an exact lookup failing on a byte-identical value. What "equality" reaches is now backend-dependent, which the arm's docstring states; on MariaDB both disjuncts run under `utf8mb4_unicode_ci` and reach further than either sentence implies.
3. **The message body ends at the first RS *or* the first EOT.** The contract says "truncated at the first RS." The `RS EOT` trailer's two characters arrive as separate keystrokes from a wedge, so `<data> EOT` is a reachable shape, and reading the terminator as data glued `'\x04'` onto the last record — not whitespace, so no trim removed it — turning a character-for-character catalog match into no product and no hits, and handing 4.5 a create form pre-filled with a control character. This is not the separator tolerance the Never list forbids: it changes no scan's `kind` and invents no envelope.

**Shape sketch** (the grammar, not the docstrings):

```python
_DATA_IDENTIFIER_RE = re.compile(r'(\d*[A-Z])')     # <digits?><one uppercase letter>
ECIA_FIELD_KEYS = ('P', '1P', 'Q', 'K', '1K', '9D', '10D')   # AD-15, exactly

def parse_fields(value):
    if not isinstance(value, str):
        raise TypeError(...)                         # caller fault, value not interpolated
    if not is_envelope(value):
        return {}
    body = value[len(_HEADER):].split(_RS, 1)[0]     # RS terminates format 06
    fields = {}
    for element in body.split(_GS):
        m = _DATA_IDENTIFIER_RE.match(element)
        if not m:
            continue
        di, data = m.group(1), element[m.end():]
        if di in ECIA_FIELD_KEYS and data and di not in fields:   # first wins
            fields[di] = data                        # verbatim
    return fields
```
