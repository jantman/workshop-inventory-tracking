## Intent

**Problem:** Epic 4 built the whole identification loop except its last link. `CatalogService.resolve_scan()` classifies, looks up and falls through correctly for all four FR36 kinds (`app/mariadb_catalog_service.py:2072`), but nothing calls it: `POST /api/scan` still echoes `{'success': True, 'raw': cleaned, 'outcome': 'unrouted'}` and deliberately constructs no service (`app/main/routes.py:1080-1142`, pinned by `tests/unit/test_scan_routes.py:264-284`), and the client discards the response body entirely (`app/static/js/scan-capture.js:225-226`). So every scan is still a no-op: FR40 (an unmatched scan lands on a create form with the identifier attached and typed), FR39 (a distributor scan pre-fills MPN, quantity and order references) and FR41 (a matched scan in a receiving context offers to add a Purchase, and a duplicate requires explicit confirmation) are all unbuilt. The destinations they need do not exist either — the create form reads a `form_data` dict but never consults `request.args` (`app/main/routes.py:867-869`), there is no HTML Purchase form at all (only the JSON `api_record_purchase`, `:989`), no identifier reaches the UI anywhere (`add_identifier` has zero route callers), and `search_products()` has no HTML consumer.

**Approach:** Make the route the router. `api_scan` calls `resolve_scan(cleaned)` and turns the returned `ScanResolution` into one server-built destination URL plus a named `outcome`; the client's only new behavior is to follow that URL (the `api_record_purchase` precedent at `app/main/routes.py:1049`, which already returns `product_url` for the client to navigate to). Then build the three landings that URL can point at: the existing create form gains query-string pre-fill, a scanned-identifier block that is attached on save, and an optional first-receipt block; the product detail page gains a scan-arrival banner offering "add a purchase" and a confirm-gated "create a separate product instead"; and a minimal `/products/search` results page renders `search_products()` hits so an ambiguous scan lands on a list. No scan classification moves to the client, and no service method changes.

## Boundaries & Constraints

**Always:**
- **`POST /api/scan` stays read-only and stays the only scan seam.** It calls `resolve_scan(cleaned)` once and writes nothing — no Purchase, no Product, no identifier, no audit mutation. Every mutation in this story happens through a separate, ordinary, CSRF-protected HTML form POST. This is what keeps the existing `@csrf.exempt` (`app/main/routes.py:1081`) defensible and is why deferred-work `:136` (at-least-once transport), `:144` (CSRF) and `:148` (rate limiting) — all three aimed at "the story that first gives the endpoint an effect" — stay open rather than being closed here.
- **The success envelope grows to exactly six keys**, replacing the three that `tests/unit/test_scan_routes.py:279-284` pins: `{'success': True, 'raw': cleaned, 'kind': <ScanKind value>, 'outcome': <str>, 'url': <str>, 'hit_count': <int>}`. `kind` is `classification.kind.value` — the serialization `app/models.py:145-150` already predicted this story would add. `outcome` is one of exactly three strings, decided solely from the resolution:
  - `resolution.product is not None` → `'product'`, `url` = the product detail page.
  - `product is None` and `free_text_hits` non-empty → `'search'`, `url` = the results page.
  - `product is None` and `free_text_hits` empty → `'create'`, `url` = the pre-filled create form.
  `hit_count` is `len(resolution.free_text_hits)`; `url` is always non-empty, so **no scan dead-ends** (FR36/FR40). `'unrouted'` is retired.
- **URLs are built server-side with `url_for`, never assembled in JS or in a template** (AD-5: the client never classifies; AD-2: routes own the envelope). A single module-level helper in `app/main/routes.py` maps a `ScanResolution` to `(outcome, url)` and is the one place the mapping lives.
- **Detached-row discipline.** `resolution.product` and every element of `free_text_hits` are detached `Product` ORM rows (`app/mariadb_catalog_service.py:2311-2318`, `1917-1920`). Read scalar columns only — never a relationship — and never `dataclasses.asdict()`/`copy.deepcopy()` a `ScanClassification`/`ScanResolution`, which raise on the `mappingproxy` (`app/models.py:488-498`, `713-718`). The response needs `product.id` and nothing else; the detail page re-fetches through `get_product()` as it already does.
- **Pre-fill is query-string, verbatim, and always editable** (FR39). Every pre-filled value arrives as a normal `request.args` entry, is rendered into an ordinary editable `<input>`, and is read on GET only. `product_add`'s GET populates `form_data` from a fixed whitelist of arg names instead of `{}` (`app/main/routes.py:867-869`); the templates already read every value from `form_data`, so no existing field's markup changes. Values are taken as given — length is judged by `_validate_product_form` on POST (`:764`), not silently truncated on GET.
- **The scan → pre-fill mapping, stated once:**
  | classification | create-form pre-fill |
  |---|---|
  | `gtin` | `identifier_type='GTIN'` (the `IdentifierType.GTIN.value` literal, which is upper-case — `app/models.py:125`), `identifier_value=<normalized 14-digit>`; description blank |
  | `ecia` | `mpn` ← first non-blank of `1P`, `P`; `vendor_sku` ← `P` when `P` was not used for `mpn`; `quantity` ← `Q`; `order_number` ← first non-blank of `K`, `1K`; no identifier |
  | `internal`, `free_text` | `description` ← the AIM-stripped raw scan, so the scan is not lost; no identifier |
  All ECIA values are pre-filled from a **`.strip()`ed copy** — `parse_fields` keeps values verbatim (`app/utils/ecia.py`) and a padded value would otherwise be saved with its padding. This closes deferred-work `:242`, which explicitly left the choice to this story.
- **The `q` on a `search` URL is re-derived, and the derivation is pinned by a test.** AD-15 freezes `ScanResolution` to three fields, so the text `resolve_scan` actually searched is not returned and a fourth field must not be added. It is, however, a pure function of `classification`, and the route re-derives it in a `_scan_search_text(classification)` helper that mirrors `app/mariadb_catalog_service.py:2319`/`:2341`/`:2455`/`:2461` exactly: `internal` → `normalized_value`; `gtin` and `free_text` → `scan_router.strip_aim_prefix(classification.raw)`; `ecia` → the first non-blank of `.strip()`ed `1P`, `P`. Because this is a second copy of a service-internal rule, a unit test asserts for **every** kind that `search_products(_scan_search_text(c))` returns exactly `resolve_scan(raw).free_text_hits` — so the search page can never show a different set than `hit_count` promised, and a change to either rule turns the test red. Importing `scan_router` into `app/main/routes.py` for `strip_aim_prefix` is a pure-util call, not classification (AD-4).
- **`identifier_type` / `identifier_value` are only ever emitted for `gtin`.** `INTERNAL` is refused by `add_identifier` (`app/mariadb_catalog_service.py:1655`); `ecia` puts the part number in `products.mpn`, which `resolve_scan`'s ECIA arm already queries alongside `MPN` identifier rows (`:2343`), so a second global-scoped `MPN` identifier row would add nothing and would collide across legitimately distinct products; `free_text` offers no type to infer. FR40's "type inferred" is therefore satisfied wherever the shipped classifier yields a type, and the raw scan is preserved in `description` where it does not.
- **`product_add`'s POST gains three effects, in this order, after `create_product` succeeds and beside the existing tag handling** (`app/main/routes.py:885-908`) — each non-fatal, because the Product demonstrably exists and the operator must never be told the save failed (the `_apply_product_tags` precedent at `:901-906`):
  1. If `identifier_value` is non-blank → `add_identifier(new_id, identifier_type=…, value=…)`. A `ValidationError` (including the uniqueness message the constraint produces, `:1717-1723`) is flashed as an `error` and the operator is redirected to the new product — it is not re-raised and does not roll the Product back.
  2. If any of `quantity`, `order_number`, `vendor`, `vendor_sku` is non-blank → one `record_purchase(new_id, …)` recording the first receipt. It returns `None` on failure (`:1385`), which is flashed as an `error`; it never raises.
  3. Redirect to `main.product_detail` exactly as today.
- **Duplicate confirmation is a server-side gate** (FR41), on the `inventory_shorten` precedent (`app/main/routes.py:1689`, `1701-1702`; checkbox at `app/templates/inventory/shorten.html:190`). The create form carries a hidden `duplicate_of` field; when it is non-blank and the submitted `confirm_duplicate` is not `'yes'`, the POST re-renders the form with `validation_errors['confirm_duplicate']` and writes nothing. `_validate_product_form` owns the check so every caller of it inherits the rule; it also gains the two receipt-field rules it must own for the same reason — `quantity`, if non-blank, must parse as an integer greater than zero, and `vendor`, `vendor_sku` and `order_number` are each capped at 255 to match their `Purchase` columns (`app/database.py:889`), with messages in the existing `'{label} …'` wording. The banner states plainly that the scanned identifier stays with the existing product, because `uq_product_identifiers_type_value_scope` (`app/database.py:1043`) makes a GTIN globally unique — the confirmed duplicate is created, and effect 1 above flashes that the identifier could not be attached.
- **The detail page's scan banner is built by the route, rendered by the template.** `product_detail` reads a fixed set of `request.args` (`scan_kind`, `scan_type`, `scan_value`, `quantity`, `order_number`, `vendor_sku`), and when `scan_kind` is present passes a `scan_banner` dict holding the two `url_for`-built links — "Add a purchase" (the purchase form, pre-filled) and "Create a separate product instead" (the create form with `duplicate_of` set). The template renders a Bootstrap alert and two links and computes no URL itself. Absent `scan_kind`, the page is byte-identical to today.
- **Two new HTML routes in the `main` blueprint, both ordinary CSRF-protected pages:**
  - `GET /products/search` → `main.product_search`. Reads `q` (`request.args.get('q', '').strip()`, the convention at `:1825`), calls `search_products(q)` and nothing else (AD-17), renders the hits as links to `main.product_detail`. Blank `q` renders the empty state without querying. Forwards the create-pre-fill args it was given into a single `create_url` so "Create a new product" from a results page keeps the scan's pre-fill — the reason the scan endpoint puts those args on the search URL too.
  - `GET, POST /products/<int:product_id>/purchases/add` → `main.purchase_add`. 404s on an unknown product. GET pre-fills from `request.args` (`vendor`, `vendor_sku`, `order_date`, `received_date`, `quantity`, `unit_price`, `order_number`, `source_url`). POST parses with the same conversions `api_record_purchase` already uses (`Decimal(str(...))`, `int(...)`, `date.fromisoformat(...)`, `:989-1069`), re-renders with field errors on a bad value, calls `record_purchase`, then flashes and redirects to `main.product_detail`. The JSON `api_record_purchase` is not touched and keeps its own contract.
- **`scan-capture.js` change is one branch.** On a success response, after the existing clear-and-refocus, navigate with `window.location.href = data.url` when `data.url` is a non-empty string (the `main.js:233` precedent). Navigate only for the response belonging to the scan currently in flight — the existing `inFlightText` / late-response guards (`:220-236`, `:262-286`) must keep `TestLateResponseDoesNotClobberTheOperator` green — and never on an error envelope. No classification, no URL construction, no parsing of `kind`/`outcome` to decide where to go.
- **Tests.** Unit: `tests/unit/test_scan_routes.py` updated for the new envelope and for the endpoint now constructing a service, plus a class per outcome asserting the exact `url`; `tests/unit/test_product_routes.py` extended for GET pre-fill, identifier attach (success and uniqueness collision), first-receipt recording, the duplicate gate, the search page and the purchase form. E2E: `tests/e2e/test_wedge_scan.py`'s stubs updated so a stubbed success no longer means "nothing happens", and a new `tests/e2e/test_scan_routing.py` walking a real scan of each outcome to its landing page. `@pytest.mark.unit` / `@pytest.mark.e2e`, `Test*` classes, existing `client`/`test_storage`/`live_server`/`page` fixtures, no mocking of the service or the ORM. Docstrings cite FR36/FR39/FR40/FR41/AD-2/AD-5/AD-15/AD-17.

**Block If:**
- Satisfying FR39/FR40/FR41 appears to require a new or changed field on `ScanClassification`/`ScanResolution`, or a new `ScanKind` member — AD-15 freezes both shapes for Epics 4, 7, 8 and 9 (this is exactly what deferred-work `:194` says about signalling a truncated result set); widening them is a human decision.
- A schema migration appears necessary. No new column, table or index is implied (AD-14); the Alembic head must still be `68707d1f48bf`.
- Attaching a scanned identifier appears to require relaxing `uq_product_identifiers_type_value_scope`, moving an identifier between Products, or otherwise changing `add_identifier`'s uniqueness semantics.

**Never:**
- `app/utils/scan_router.py`, `app/utils/ecia.py`, `app/utils/gs1.py`, `app/utils/gtin.py`, `app/models.py`, `app/database.py` and `app/mariadb_catalog_service.py` are **read-only in this story**. 4.5 is a consumer: it adds no service method and changes no existing one. - No second search implementation and no search *mechanism* work: `/products/search` calls `search_products(q)` with no filters, no paging, no ranking, no facets, and no result-count signal. LIKE-vs-FULLTEXT, ranking, paging and the 50-row bound (deferred-work `:194`, `:210`) are Epic 8's decisions under AD-17 and stay open.
- No client-side classification or URL building (AD-5). The JS reads `data.url` and follows it; it must not branch on `kind` to choose a destination.
- No relocation or refactor of `_SCAN_TRIM` / `_clean_scan_input` / `ScanCapture.stripOuter` (deferred-work `:132`), and no absorption of a leading separator before an ECIA header (`:171`). Both still want the physical Tera HW0009, and absorbing separators in the cleaner would be the fourth copy of the trim rule. Both stay open, re-aimed at the story that first has a real label to scan — as do `:124` (control characters in a text input), `:163` (a wedge that delivers no RS/GS) and `:246` (a multi-format 15434 label).
- No date coercion from `9D`/`10D`. They are `YYWW` — a week, not a day — so nothing pre-fills `order_date` or `received_date` from a scan; inventing a day would be a guess the operator cannot see. `Q` is pre-filled as the scanned string and parsed by the form like any typed value.
- No ASIN or `GTIN_UNVALIDATED` inference. The shipped classifier has no ASIN arm and gives no signal that a rejected check digit was intended as a GTIN; guessing either would attach a wrong-typed identifier.
- No change to `POST /api/products/<int:product_id>/purchases`, to `main.js`, to `inventory-add.js`, or to anything under `app/main/` serving the metal-stock inventory (NFR9) — the JA-ID lookup and the existing barcode flows must stay green untouched.
- No new runtime dependency, and no change to `app/templates/base.html` (the scan field and its script tag stay exactly as Story 4.1 left them).

## Design Notes

**Why the route returns a URL instead of the client building one.** AD-5 binds "every surface that accepts a scan" and its Prevents clause names the exact hazard: "client JS and multiple routes classifying the same scan differently." If the client branched on `kind` to pick a destination, the FR36 precedence would exist in two languages and Epic 9's handheld view would be a third. Returning one server-built `url` keeps `url_for` — and therefore the URL namespace — inside the blueprint, makes every routing decision assertable from a unit test with no browser, and leaves the client with a single line of new behavior. `api_record_purchase` already established the shape (`app/main/routes.py:1049` returns `product_url`), so this is the codebase's own idiom rather than a new one.

**Why `POST /api/scan` stays read-only, and what that buys.** Three open ledger entries (`:136` at-least-once transport, `:144` the CSRF exemption, `:148` rate limiting) were each deferred with the same reasoning: they matter "once the endpoint has an effect." The natural design for this story would be for the scan to *do* something — record the receipt, create the product. Keeping it a pure lookup that answers with a destination means a duplicated scan burst costs one extra SELECT and nothing else, so the CSRF exemption stays defensible and all three entries stay honestly open instead of being force-closed. Every mutation this story adds sits behind an ordinary CSRF-protected form POST that an operator submits deliberately.

**Why "receiving context" is the banner, not a mode.** FR41 says a scan resolving to an existing Product "during receipt" offers to add a Purchase. There is no receipt mode in this application and inventing one — a toggle, a session flag, a separate scan endpoint — would be a product decision nobody has taken. Landing every matched scan on the product record (which is what the epic's own UX note asks for: "a match lands on the record") and offering "Add a purchase" in the arrival banner makes the receiving context the operator's next click. It satisfies FR41 without a mode, and Epic 9's self-sufficient scan-result view can replace the banner without unpicking a state machine.

**Why a confirmed duplicate does not carry the identifier.** `uq_product_identifiers_type_value_scope` (`app/database.py:1043`) makes a `GTIN` globally unique, so "create a duplicate anyway" and "attach the scanned GTIN to it" are mutually exclusive at the schema level. Rather than pretend otherwise, the banner says so before the click and the create POST flashes it after: the Product is created, the identifier stays with the original. The alternative — moving the identifier — would silently rewrite the first product's identity from a form that never mentioned it, and `add_identifier` deliberately offers no such operation. This is also why the attach failure is non-fatal: `create_product` has already committed by then (`app/mariadb_catalog_service.py:256`), and telling the operator the save failed while the Product exists is the failure mode `_apply_product_tags` was already written to avoid (`app/main/routes.py:901-906`).

**Why ECIA pre-fills `products.mpn` and attaches no identifier row.** `resolve_scan`'s ECIA arm already queries `products.mpn` **or** an `MPN` identifier row (`:2343`), so setting the column alone makes the next scan of the same label resolve — the identifier row would add no reachability. It would, however, add a collision: `MPN` is not vendor-scoped (`app/models.py:174`), so the row is globally unique, and two genuinely distinct products sharing a manufacturer part number is exactly the case Story 4.4's Design Notes documented as the reason its lookup falls through on ambiguity. Writing the free column and not the unique row keeps that ambiguity representable.

**Why dates are not pre-filled.** `9D`/`10D` are `YYWW` per the PRD addendum (`addendum.md:27`) — a week, with no day in it. Story 4.4 deliberately did not coerce them, and a form field pre-filled with a manufactured day would look like scanned data while being a guess. The epic's own AC lists "MPN, quantity, and order references" and no date, so nothing is lost by leaving `order_date` and `received_date` blank for the operator.

**Why `/products/search` and not a scan-only results page.** AD-17 fixes `search_products()` as the sole entrypoint and defers the *mechanism* to Epic 8; Epic 8 Story 8.1 then owns the search page. A `/scan/results` page would be a URL Epic 8 has to orphan, whereas `/products/search?q=` is the namespace Epic 8 will extend with facets and bookmarkable state (Story 8.2). Shipping the minimum there — a query, a list, an empty state, a create escape hatch — gives the scan fallthrough its landing and leaves Epic 8 adding to a page rather than replacing one. The 50-row cap and the substring semantics (deferred-work `:194`, `:210`) are visible on this page and stay open, unchanged.
