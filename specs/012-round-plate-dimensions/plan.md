# Implementation Plan: Round Plate Dimensions

**Branch**: `issues/85` | **Date**: 2026-08-10 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/012-round-plate-dimensions/spec.md`

## Summary

A round Plate or Sheet stops requiring a Length and starts requiring only Diameter and
Thickness. Diameter is the `width` column, as it already is for every round item, so nothing
in the schema changes and there is no migration.

The work is larger than that sentence because the requirement it corrects is stated in three
places that disagree, only one of which runs, and because the operator chose to have the rules
enforced on every write path rather than only marked on the Add form. So the shape of the
change is: **collapse the three statements into one, enforce that one everywhere an item can
be recorded, and fix the display paths that assume every item has a length.**

See [research.md](./research.md) for the eight decisions behind this, each with what was
observed in the code to settle it.

## Technical Context

**Language/Version**: Python 3.13 (nox sessions pin it; system Python is 3.14)

**Primary Dependencies**: Flask 3.1.x (app-factory), SQLAlchemy 2.0.x (legacy `Query` style),
Jinja2 + Bootstrap 5.3.2, vanilla ES6 — no build step, no frontend framework

**Storage**: MariaDB via PyMySQL in production, SQLite through the same `Storage` ABC in unit
tests. **No schema change and no Alembic revision** — `length` is already
`Column(Numeric(10, 4), nullable=True)` (`app/database.py:42`) and the positive-value
`CheckConstraint`s (`:85-89`) already permit NULL.

**Testing**: `nox -s tests` (pytest, network blocked), `nox -s e2e` (Playwright,
`-m "e2e and not screenshot"`, 15-minute tool timeout, run in background — the tool clamps at
10 minutes), `nox -s screenshots_headless` + `screenshots_verify`. No new pytest marker.

**Target Platform**: Linux, home LAN, single trusted user, no authentication

**Project Type**: Server-rendered Flask web application

**Performance Goals**: None. Nothing here is on a measured hot path, and Constitution
Principle I bars optimizing without a measurement. The one performance-adjacent decision —
rendering the rules into the page rather than fetching them (D4) — is made to avoid adding an
asynchronous boundary to the e2e suite, not to save milliseconds.

**Constraints**: `Decimal` only for measurements, never `float` (Principle III). E2E tests
wait on observable state, never on elapsed time (Principle IV). Touching
`app/templates/**`, `app/static/js/**` or `app/static/css/**` obliges regenerating
documentation screenshots in the same change (Development Workflow).

**Scale/Scope**: One user, one workshop. Six source files, two templates, one new front-end
module, and the tests and screenshots that follow them.

## Design in brief

Full detail is in [data-model.md](./data-model.md) and
[contracts/dimension-rules.md](./contracts/dimension-rules.md). The shape of it:

1. **One table, keyed on Type *and* Shape.** `app/taxonomy.py`'s `required_dimensions` is
   keyed on type alone today and structurally cannot express "a round plate differs from a
   rectangular one", which is why the rule ended up restated in JavaScript. The dataclass gains
   per-shape requirements. The table is seeded to reproduce today's *effective* behaviour —
   the JS table, because it is the only one that runs — with exactly two rows changed.

2. **`validate_dimensions()` in the same module**, returning every missing dimension rather
   than the first (FR-018). Called from the Add POST, the Edit POST and the JSON create path,
   beside the `required_fields` check already there. Deliberately *not* called from
   `InventoryService`, because e2e fixtures seed through it — see D2.

3. **`InventoryItem.validate()` delegates** to the same function, deleting the third copy.

4. **The front end reads the table, it does not restate it.** The views pass it to the
   templates as JSON; `dimension-requirements.js` applies it on both forms — setting
   `required`, showing the `*`, relabelling Width to Diameter for round shapes, and filtering
   the Shape options. `inventory-add.js` loses its literal; `edit.html` loses its hand-rolled
   label swapping and gains enforcement it never had.

5. **Display paths stop assuming a length.** Two real defects, both of which would make a
   correctly recorded round plate look broken:
   - `display_name` (`app/database.py:257`) puts every dimension behind `if self.length:`, so
     a length-less round plate renders as `Steel Plate Round` with no dimensions at all. It
     reaches five API payloads and every screen that shows an item's name.
   - `formatFullDimensions` (`app/static/js/components/item-formatters.js:61`) emits ⌀ only on
     the branch where width appears *without* thickness, so a round plate carrying both renders
     `6" × 0.25"` — identical to a rectangular one. This is already wrong today; FR-014
     forbids it.

## Complexity Tracking

| Expansion | Why needed | Simpler alternative rejected because |
|---|---|---|
| Dimension rules enforced on every write path, not just marked on the Add form | The operator chose it, with the risk stated, over both narrower options. FR-017/FR-018 were added to the spec to match rather than leave plan and spec contradicting. Without it the item API keeps accepting a round plate with no thickness, which FR-006 forbids. | *Forms only, as today* was offered as the recommended option and declined. *Enforce for round Plate and Sheet alone* was offered and declined — it would have had no blast radius at all, at the cost of a server that validates one combination and ignores the other twenty. |
| A new shared front-end module rather than editing the two forms in place | FR-007 requires each form's requirement marks to match what it enforces. The Edit form marks `Length *` and `Width *`, enforces neither (no input carries `required`), and never marks Thickness — so it needs real logic regardless of this feature. Two genuine call sites. | Writing a second copy of the logic inside `edit.html` would recreate in JavaScript exactly the triplication being removed from Python — the bug this feature exists to fix. Deleting the Edit form's asterisks instead would satisfy FR-007 literally while making the form worse and leaving the operator to discover requirements from a server rejection. |

Both are recorded rather than absorbed, because Principle I asks whether this is the simplest
thing that works and a reviewer is entitled to disagree with either.

## Known gaps this feature does not close

Recorded so they are visible rather than discovered later. None is required by the spec.

- **`app/mariadb_inventory_service.py:500`** — `if current_db_item.length and new_length >= ...`
  short-circuits, so an item with no length passes the "must be shorter" check and is assigned
  one. Unreachable today: `_process_shortening` (`app/main/routes.py:2153-2159`) refuses a
  length-less item first, and `inventory-shorten.js:192` refuses it client-side. It is listed
  because round plates make NULL length ordinary rather than exotic, so the latent hole gets
  closer to the surface.
- **Dead reads of a `diameter` key.** `inventory-search.js:647` and `history-viewer.js:210-212`
  render `dimensions.diameter`, `inner_diameter` and `outer_diameter`; no serializer emits any
  of them. A round item's diameter surfaces in those modals as a row labelled "Width". Cosmetic,
  pre-existing, and not what FR-014 is about — that clause is satisfied where the ⌀ is fixed.
- **Channel still requires no dimensions.** Carried forward deliberately (spec, Out of Scope).
  The one visible side effect — Channel's Shape dropdown narrowing to the shapes it is recorded
  as taking — is called out in the spec.
- **`Dimensions.volume()`** returns `None` without a length, so a round plate has no estimated
  volume even though diameter and thickness determine it. `estimated_volume` is read nowhere in
  the application, so this is invisible.
