# Research: Outstanding Products Page

No NEEDS CLARIFICATION items came out of Technical Context. These are the design decisions.

## R1: Where the receipt logic lives

- **Decision**: Add `CatalogService.receive_purchases(purchase_ids, received_date=None)`.
  Move the body of `receive_order_lines` into a private `_receive_lines(ids, received_date,
  scope)`, where `scope` is an optional `(vendor, order_number)`. Both public methods call it.
- **Rationale**: Everything except the order restriction is the same: id parsing, the
  "tick something" rule, date parsing, the existence check, validating every line before
  changing any, then `_apply_receipt`. A single core means a fix to bulk receiving reaches
  both pages.
- **Alternatives**: (a) Call `receive_order_lines` once per order. Rejected: that is one
  transaction per order, which breaks the all-or-nothing rule (FR-009). (b) Copy the method.
  Rejected: the two copies would drift.

## R2: Client-side code

- **Decision**: Reuse `order-bulk-actions.js` unchanged. The new page renders the same ids
  and classes that the script reads.
- **Rationale**: The script is generic "line selection + label dialog + receive button
  arming", and only its names mention orders. A page of lines from many orders is still a
  page of order lines. Keeping the DOM contract means no new JS and no new JS tests.
- **Alternatives**: Parametrize the script by a root element or prefix. Rejected: that adds
  an abstraction to support two callers that render identical markup anyway.

## R3: Sharing the toolbar markup

- **Decision**: Extract the toolbar (Print Labels button and count, receive form, date and
  help text) into the `order_bulk_toolbar(action_url)` macro in
  `product/_order_bulk_toolbar.html`. Use it from `order.html` and `outstanding.html`.
- **Rationale**: The JS depends on these ids, so the two pages must render identical
  markup. One macro guarantees that. The repo already uses this pattern
  (`_bulk_label_modal.html`).

## R4: What counts as outstanding, and ordering

- **Decision**: Outstanding means `received_date IS NULL`, the same as
  `Purchase.is_outstanding` and the reorder list's "on order" clause. Sort in Python by
  `(no order number, order_date is None, order_date, vendor, order number, id)`.
- **Rationale**: Sorting in Python handles NULL dates the same way on SQLite and MariaDB.
  `find_captured_orders` sorts in Python for the same reason. Lines of one order share
  their vendor, number and (normally) date, so they sort together. Oldest first puts the
  longest-waiting lines at the top.
- **Alternatives**: Group by product. Rejected: the spec's unit is the purchase line,
  because two outstanding purchases of one product are two receipts.

## R5: Order link for a row

- **Decision**: Link to `product.order_detail(vendor, order_number)` when
  `supplier_order_reference` is set. Otherwise show "no order".
- **Rationale**: That is the route every vendor's order shares (029).

## R6: Screenshot

- **Decision**: Add a screenshot of the new page (`user-manual/outstanding_products.png`),
  generated by `nox -s screenshots`, and use it in the new manual section. Commit only the
  screenshots whose content this feature changes. Other images churn on every run without
  any real change.
- **Rationale**: Constitution: UI changes come with screenshots. The CI screenshot job only
  posts a reminder.
