# Implementation Plan: Outstanding Products Page

**Branch**: `robot-army/issue-200-outstanding-product-receiving-page` | **Date**: 2026-10-10 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/062-outstanding-products/spec.md`

## Summary

A new page, `GET /products/outstanding` (Products → Outstanding Products), lists every
purchase with no received date, from every vendor and order. That includes purchases with
no order number. Rows are grouped by order, with the oldest order first. The page uses the
same selection, toolbar and label dialog as the order page from feature 060:

1. **Print Labels** opens the shared `BulkLabelPrintDialog`, which posts to the existing
   `/api/products/<id>/label` endpoint once per distinct product.
2. **Receive Selected** is a plain form POST to `/products/outstanding/receive`. It carries
   the ticked purchase ids and one date. A new service method,
   `CatalogService.receive_purchases(...)`, receives them in one session, so the receipt is
   all-or-nothing. The page then redirects back to itself with a received/skipped flash.

`receive_order_lines` (060) and `receive_purchases` share one private helper, `_receive_lines`.
The only difference between them is that the order version also restricts the ids to one
order. Both apply each receipt through `_apply_receipt`, so receiving a line from this page
is identical to receiving it from the order page or the single-receipt screen (SC-003).

The client side needs **no new JavaScript**. The new page keeps the DOM contract that
`order-bulk-actions.js` already reads (`#order-lines`, `.order-line-checkbox`,
`#order-select-all`, the toolbar ids and the modal id). The toolbar markup moves into a
macro (`product/_order_bulk_toolbar.html`) used by both pages, so the two cannot drift
apart.

## Technical Context

**Language/Version**: Python 3.13 (Flask), vanilla JavaScript (unchanged)

**Primary Dependencies**: Flask, SQLAlchemy, Bootstrap 5. Nothing new.

**Storage**: MariaDB, existing `purchases` and `products` tables. No schema change.

**Testing**: pytest unit tests via `nox -s tests`; Playwright e2e via `nox -s e2e`

**Target Platform**: LAN web app

**Project Type**: web application (server-rendered)

**Performance Goals / Constraints / Scale**: N/A. At most tens of outstanding lines. One
query with `selectinload(Purchase.product)`, the same as `find_order_lines_for`.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Assessment |
|---|---|
| **I. Simplicity First** | ✅ No new JS, endpoint or dependency for labels. One page, one read method and one receive method, which share their core with 060's method instead of copying it. The toolbar macro replaces markup that would otherwise be duplicated. No filtering, paging or caching. |
| **II. Layered Architecture** | ✅ The query and the receipt live in `CatalogService`. The routes only read the form, call the service, flash, and render or redirect. |
| **III. Exact Numerics** | ✅ Quantities are the stored integer purchase quantities. No measurement arithmetic. |
| **IV. Test Discipline** | ✅ Unit tests cover the read (outstanding only, order grouping, no-order last) and the receive (parity with single receipt, cross-order, skip, all-or-nothing on a bad date or a missing id), plus the routes. The e2e tests cover cross-order receive, label dedup, selection and the nav link. They wait on rendered state with `expect` and seed data directly. One new screenshot is generated by `nox -s screenshots`, not by e2e. |
| **V. MariaDB Source of Truth** | ✅ No schema change. One transaction per bulk receipt. |
| **VI. Item Lifecycle Invariants** | ✅ N/A. These are purchases and products, not JA-ID items. |
| **Threat model** | ✅ Posted ids are checked to exist so that a stale page fails cleanly. This is for correctness, not defense. The form carries a CSRF token like every other form. |

**Post-design re-check**: ✅ Unchanged after Phase 1. No violations.
